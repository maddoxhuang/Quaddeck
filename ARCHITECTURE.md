# QuadDeck 1.5.0 architecture

## Single-instance external file opening

`main.cpp` handles the existing explicit file-registration switches before
single-instance election. All other launches use `SingleInstance` before
constructing App or a player window. Its lifetime mutex is in the Windows
session namespace and its mutex/pipe names include the current user SID and
session ID. Production has one fixed namespace, with no command-line or environment override.

The local named pipe has a logon-SID DACL, rejects remote clients and verifies
the peer process's user and session on both ends. Client rights are specified
individually rather than granting generic write/create-instance access. The
first-pipe-instance flag prevents a second listener from silently sharing the
endpoint. This follows Microsoft's
[named-pipe security guidance](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).
No persisted secret, TCP listener or association/settings change is needed.

The versioned, length-delimited protocol carries only a request ID and a bounded
list of UTF-16 filesystem paths, or an empty list to activate the window.
Paths are normalized syntactically in the sender's working directory; URLs,
Emby locators, device paths and control switches are not playback requests.
`main.cpp` leaves such an argument out with one warning rather than failing
the launch. A device is refused only as a whole path component (trailing dots
and spaces dropped): `Con.Air.1997.mkv` is an ordinary file on Windows 11 and
on shares, and where older Windows maps a device name with an extension to
`\\.\CON`, `GetFullPathNameW` has already produced a path the syntax check
refuses.
Drive and UNC filesystem paths are supported without resolving a network file
on the window thread. Limits are 256 paths and 512 KiB per request, 64 pending
requests and 2 MiB of pending payload. An ACK means the complete request has
been reserved and queued in memory. Its reservation survives UI dequeue until
`completeRequest`; pending IDs and completed IDs retained for 60 seconds make
bounded sender retries idempotent. A full queue/cache returns a failure rather
than discarding files. Delivery is not durable across a receiving-process crash.

Only the elected owner creates the player. A secondary waits through startup
and retries with the same ID for a bounded interval; a dead owner's abandoned
mutex allows takeover. An alive but unavailable receiver causes a clear error
instead of another player window. The sender grants foreground permission only
to the verified receiver PID; the window thread restores a minimized receiver,
tries to foreground it and flashes its taskbar entry when Windows refuses.
Shutdown stops and joins the listener before clearing the App queue, while the
mutex remains owned through App teardown. Recoverable early client disconnects
restart the accept loop instead of stranding an alive owner without a listener.

App drains accepted batches on its window thread. The startup files are the
first batch. While no pane is loaded (a fresh launch, or a window whose videos
were all closed), `openExternalDeck` gives the batch to `loadFiles` as the
command line did before single-instance -- up to five panes, the saved seek
mode and audio mask, the rest reported -- and then starts it as Space does
(the command line used to leave it paused). Several files handed to one launch
are a comparison deck, and an empty running window behaves like no window at
all. Otherwise the batch takes the local Plan A Add path. It never replaces an
active manual local/Emby chooser. Existing normalized local paths select their
pane without reopening or changing audio, pause or progress, and make that
pane visible. New paths occupy empty panes, muted, with independent local
queues; the first Add adopts a startup pane into its folder queue as it does
for a manual open. A full five-pane deck pauses on the existing local
thumbnail/title chooser. Cancel discards the current external batch's remaining
files while preserving later independent batches and all playing panes.
Manual F6 Add retains its same-file duplication and cancellation behavior.
A subtitle file (`isSubtitleExtension`) in a batch is never a pane of its own.
With video showing, `openExternalSubtitle` puts it on the local pane whose
video it belongs to by the sidecar rule (same folder, `subtitleNameFitsVideo`,
the longest name, `externalSubtitleVideoPane`), else on `subtitlePane()`,
through `addSubtitleFile` as a drop does: the viewer's choice. A
`subtitlePane()` that is still opening (an Emby item resolving) gets a
notice, never another pane. When a video it fits better than any open one is
still queued -- later in its batch, or in a batch behind it, since Explorer
starts one launch per selected file -- `deferExternalSubtitle` moves the
subtitle after that video and after the subtitles moved there before it
(`ExternalOpenBatch::deferred`), ahead of those that came with the video, so
they go on it in the order they came. Because the video's launch can arrive
a few ticks later, a subtitle with no fitting open video, or only one whose
name is shorter than another it could fit (a dot after the open name), holds
its batch for up to `kExternalSubtitleWaitMs` (750 ms) from the batch's
arrival before falling back. `openExternalDeck` opens the batch's videos and
leaves its subtitles at the end of the batch, for the passes above. A batch of subtitles alone into an empty deck
first defers to a queued video of its name, as above; failing that, after the
wait, `findExternalSubtitleVideo` lists its folder on a detached thread
(`std::filesystem::path::parent_path`, so a drive root is the root;
`scanLocalFolder`, `videoForSubtitle`), later batches wait behind it
(`externalSubtitleLookup_`), and the video found is put into the batch ahead
of the subtitle, so the deck opens it and then the subtitle goes on it. None
found is a notice; a video opened meanwhile takes the subtitle instead, and a
video launched meanwhile is taken over the folder's. The read says so on the
status line. A folder that does not answer holds a batch queued behind it for
at most `kExternalSubtitleLookupHoldMs` (10 s): then its answer is let go and
the subtitle's batch goes behind the waiting one, which opens and takes the
subtitle as a video opened meanwhile would. With nothing waiting, the read is
waited for however long it takes.
A `.qdeck` file is an exported list of video sets (Session model, below):
the first launch of a single one, and one forwarded or among a launch's
files, adds its sets to the list and shows it (`App::importVideoSets`), so
IPC still cannot replace the deck. Until 2026-11-04 a first launch restored
the session it held and a forwarded one gave a notice. The old executable has no listener: users must exit
that version themselves once before starting the new one, and file types still
registered to an older copy keep opening it until Register... is pressed again.

## UI and layout

With several panes and Independent seeking, `transportBarLayout` omits the bottom time and seek rectangles while retaining the left and right button groups; the absent rail has no hit target. This applies to manual and browser decks. For browser decks the window title also omits aggregate time. Selecting browser Linked restores the bottom rail against source seconds and the longest source duration, and takes the strips' rails away (below).

Pane rails have their own `paneTimelineWanted_` / `paneTimelineAlpha_`, independent of corner chrome. Only the hovered pane's lower-edge reveal zone wakes its rail; caption, transport row and open sheet occlude it, while an active rail drag keeps it visible. Hit testing requires both the reveal state and visible alpha, so a fading rail cannot intercept a picture click after the pointer leaves. `paneSeekAffectsAll` is shared by manual seek execution and the scope label, including paused/waiting/offset exceptions. Browser linked seeks retain their existing source-seconds alignment policy, each video at the target plus its own offset. On a per-pane deck the master clock predates each video, so the adjustment there carries when the video was opened and cannot be the offset the UI shows: `browserOffsets_` holds it instead -- the seconds a video stands ahead of the time the Linked rail aligns the videos to, 0 when its video is opened or closed. `paneOffsetSeconds` returns it on such a deck, and `setPaneOffset` and the resets go through `moveBrowserPaneOffset`, which moves that video alone: to the aligned time plus its offset (`placeBrowserPane`, waiting before its start where that is below zero) while the deck is aligned, by the change otherwise, keeping `browserSeekAligned_`. `alignBrowserPanesToTime` (the bar's rail, the arrows, a rail of a pane), Stop on a linked deck and the bar's end ticks add it; `barTime` shows the reference video's time less its offset until the first alignment. Until 2026-10-21 every alignment put every video on one time, dropping the offsets a Linked deck by hand keeps. Linked, such videos also repeat together: `paneTiming` gives none an `autoRepeat` (so none wraps alone), `embyFinishPane` and `localFinishPane` hold one that `repeatsWithLinkedVideos` (its own flag in force, or the order's Repeat it) at its end, and `finishLinkedBrowserSet`, each tick, calls `alignBrowserPanesToTime(0.0, false)` once no video plays (each held, paused, or past its end) and one held repeats. The player has two HWNDs: the main window and one video child that always receives the full client area and owns the swap chain. Everything the user sees besides the video is drawn, not a control. `Overlay` (Direct2D on the renderer's D3D11 device, DirectWrite for text) paints an `OverlayScene` onto the swap chain's back buffer each frame, invoked by the renderer between the last pane and `Present` inside the device lock; the picture is never covered by a control's background, every element is translucent and fades, and there is no child-window z-order to manage. Text is laid out once and drawn from that layout while it stays on screen: `Overlay` keeps each DirectWrite layout by its string, style, box size, alignment and wrapping -- not where the box lies, so a scrolled row keeps its own -- and each measured width by string and style, lets one go after 120 frames unused and the least recently drawn beyond 512, and drops them all when the scale changes. `OverlayLayout.hpp` holds the geometry -- the transport bar along the bottom, each pane's chrome, hit-testing -- as pure functions on floats with the DPI factor applied once. `AppChrome.cpp` builds the scene from player state, tracks hover, press and drag state, and turns pointer messages on the video child into commands.

Settings changes, whether from the settings window, the right-click menu or a key, apply directly to the same `App` state. The shader's active label derives only from the last successfully compiled preset or external file; failed compilation is transactional and leaves the previous pixel shader and status intact. The four Smart Vibrance Plus sliders map to the reference ranges and update a constant buffer immediately without recompiling the shader.

`activeLayoutCells` is the single geometry source for rendering, timeline placement, hit testing, overlay placement and drag-to-swap. It compacts only loaded panes into aspect-aware automatic, one-row, two-row, one-column, portrait-focus or landscape-focus layouts. Five-pane Auto uses a three-plus-two row split with clamped aspect-weighted widths and balanced row heights. A sole portrait source gets a narrow tall left cell with four side panes in a 2x2 grid; the inverse focus form puts a sole landscape source above a row of four portrait-friendly cells. With three or five active sources, an explicitly focused pane uses the existing left-focus geometry: two stacked side panes for three sources or a side 2x2 for five. The explicit choice survives batch additions/removals only while the active count remains three or five and the selected pane remains active. Solo remains an override. Adjustable mouse dividers are intentionally deferred because normalized weights, minimum sizes, pointer capture, reset behavior and persistence need one coherent layout-specific model.

V1-V5 are display-position names, derived from those cells top-to-bottom and then left-to-right; they are not the storage indices of `sources_`. The settings window, numeric audio shortcuts, per-pane repeat, volume/mute and Offset steppers all translate through the same order. Once all active sources have reported an aspect ratio (`paneAspectRatios`: each source's `videoDisplayAspect`, the picture's shape on screen, its pixel aspect included), App locks Auto's selected tall/wide focus until the active pane set changes. Replacing media therefore preserves the chosen physical cell even when the replacement has a different aspect ratio. Solo does not renumber the selected pane.

Explorer media drops use append-first routing. Because compact dynamic cells cover the entire client area, a hit on an existing cell is ignored while any source slot is empty; `addFiles` fills empty slots in index order. Once all five slots are occupied, the hit pane becomes the replacement target. Explicit per-pane Open/Replace commands bypass this policy.

The main and video child HWNDs forward `Alt+Enter`, media commands and mouse-wheel input into one command path. ## Time model

`PlaybackClock` is the master time. A source's local time is:

```text
(master - startDelay) * playbackRate + independentSeekAdjustment
```

It may then be held by per-source pause or wrapped by that source's A-B loop. A loop with only an A point wraps at the source's end (`loopEnd`), so setting A alone arms it; a B set later narrows it, and until the duration is known such a loop neither wraps nor counts as repeating. If no A-B loop is active, an enabled per-pane auto-repeat wraps the complete local duration only in Independent mode. Linked seeks invert the mapping; independent seeks preserve master time and change the selected source's adjustment. Master A-B loop seeks the entire clock, while a source loop seeks only that decoder when its mapped local time wraps.

Clearing an offset writes the pane's adjustment without re-aligning, so resetting all five costs one synchronized seek rather than five. A paused pane needs more than the adjustment cleared: it shows the time it is holding, and resuming rebuilds the adjustment from that held value, so the held time moves with the offset or the change is undone the moment the pane resumes.

The UI exposes the combined signed value `adjustment - startDelay * rate` as Offset. Positive values start farther into source content at master zero; negative values keep the source inactive until its mapped time reaches zero. Dragging the slider of an inactive source always changes only its adjustment, even in Linked mode, so a waiting source can be positioned directly without advancing the master clock. Legacy session delay fields remain readable.

Each source has its own rail and duration. A drag on a pane rail follows the pointer as a fraction of that rail (`railFraction`, with the rail's own inset) and commits one seek on release through `seekFromSourceBar`, always against that pane's own duration, so clips of very different lengths cannot leak master or neighbour timing into one another. In Linked mode, an active unpaused pane uses the inverse master-time mapping only when the requested source time is representable. Paused panes, waiting panes and targets earlier than a positive adjustment move that pane's Offset directly, avoiding a jump back to the earliest representable source time. Total master duration accounts for start delay, rate and adjustment. By default, reaching the total duration performs one synchronized seek to zero while preserving the playing state. A valid enabled master A-B loop takes precedence; any active source A-B loop or Independent per-pane repeat keeps the master clock running so that local wrapping can continue.

Source opening is asynchronous. While any non-failed source is still probing, the master extent is the maximum of the ready-source calculation and the previous stable duration; replacing the longest pane therefore cannot transiently look like end-of-deck. The first seek requested by `openSource` is provisional because Independent whole-file repeat cannot wrap until duration is known. When metadata becomes ready, App compares that provisional local target with the settled mapping and performs at most one correction even while paused. The provisional target is the mapping when the open began and the settled one is taken at the clock's position at ready, so while the clock plays every open, an Emby swap included, gets this second seek although no mapping changed: it is what brings the picture and the audio to where the clock has moved during the open. Comparing both at one instant would instead start the video behind the clock, catching up on screen through `frameForTime`'s drain, and the audio late by the open's duration; removing the extra seek would need the open's own request to carry its timeline instant and be re-mapped when the worker seeks. If a synchronized barrier is active, it rebuilds the complete barrier and all recorded generations rather than replacing one pane's generation in place. Previous/next-file replacement also cancels a barrier that owns the old decoder and rebuilds it at the same resumable timeline target, except that the only video's replacement starts again from zero (see "One local video is the timeline"). Only actual video progress and video/full seeks update the wrap-discontinuity tracker; audio-only seek, selection and handoff cannot consume a pending video repeat wrap.

Audio selection is a five-bit mask. Every pane owns one XAudio2 SourceVoice and all selected voices mix through the common mastering voice. Each pane also carries its own volume and mute, applied to that pane's source voice, while the mastering voice keeps master volume and mute. The two multiply rather than compete: silencing one pane leaves the others where the user put them, and the master control still governs everything at once. A muted pane keeps its trim, so unmuting restores the level rather than jumping to full. Each voice has its own queue, flush operation and frequency ratio, so changing or seeking one pane does not discard audio queued by the others. When a selected non-repeating source reaches its end before the master timeline, the app replaces only that bit with the next active, unpaused, unselected and unfinished pane in cyclic visible V1-V5 order. A repeating pane's natural Ended state remains selected because its video wrap creates a fresh audio generation; a generation-scoped Error may still hand off. Other selected voices continue uninterrupted.

Manual audio enable and automatic audio handoff call `requestAudioSeek`, which updates only the private audio demux/decoder context. They never clear `videoQueue_`, `currentFrame_` or touch the video decoder's seek generation. Full timeline movement continues to use `requestSeek`, which atomically schedules both video and audio seeks.

Source voices are persistent and their Start/Stop state is tracked idempotently. Opening a replacement is asynchronous, so it can initially fail the `ready` audio predicate; the render tick starts the fixed voice when the pane later becomes eligible. Each `VideoSource` also holds an atomic destination-voice index. Drag-to-swap retargets that index before moving the existing decoder, so it keeps synchronization state without leaving the audio callback attached to the old voice. Audio chunks carry a process-wide monotonically increasing generation because a persistent voice outlives the `VideoSource` that previously fed it. Submit, flush, voice state and timeline accounting are serialized by one mutex per voice. A flush rejects every older generation as well as physically clearing buffers, closing both sides of the race in which a stale chunk could arrive immediately before or after `FlushSourceBuffers`. Submission reports Accepted, Backpressure, Stale or Error explicitly: only Accepted may publish Primed, Backpressure retries the intact chunk, Stale abandons the superseded generation and Error terminates the current generation.

Source time is the video's for audio too: the audio worker counts from the video stream's `start_time`, rescaled into the audio stream's time base (`audioOrigin`, from its own input with the video worker's `av_find_best_stream` choice), as the picture and the subtitles do; only a file with no picture, or an attached picture, counts from the audio's own start. A file whose sound starts before its first picture (MPEG-TS, an MP4 with B-frames and no edit list) has that sound cut at source 0, and one whose sound starts later begins with silence, so the file's own offset between them is kept. `audioSeekPoint` aims no earlier than the audio's first packet, which may now lie on either side of source 0.

A generation's first audio follows the clock when it has to. `App::tick` publishes each source's mapped time, rate, whether its sound is live, the engine's output latency and the moment it sampled the clock (`VideoSource::publishClock`), stamped with the audio generation the source had then; a pending keyframe landing is not acknowledged until the owner has taken it and moved its clock. Until a generation's first buffer is accepted, the worker raises its sample gate (`AudioSampleTimeline::raiseGate`) to where that clock has got to plus the latency, so the seek and decode time the running clock did not wait for -- half a second over HTTP -- is cut rather than left to the slew; and a first buffer that starts later than it is due (a stream starting after the picture, or a clock still short of the target) gets silence in front, up to 10 s. This covers every path that starts audio with the clock running: ready alignment, fast seeks, audio enable and handoff, a keyframe landing, a per-pane wrap, a waiting pane reaching its start.

Audio drift maintenance visits every selected voice so non-reference timelines discard consumed spans during long multi-audio playback. The first voice that is currently eligible, has a usable stream and still has an XAudio2 buffer queued controls the master-clock slew; a selected bit whose video/audio has ended cannot hide a later voice that is still audible. The slew is capped at 0.5%, 5 ms a second, so it is for crystal drift, not for start offsets. Every eligible voice is measured: one more than 0.5 s from its picture (`audioNeedsReaim`; a stall that starved the voice, a gap in the stream) has its own audio sought again to the mapped time, at most every 10 s per pane and not while a repeat or loop is wrapping, and the clock and the other panes are left alone. Each audio generation's error half a second into its playing is logged once (`Audio start pane=`), and a re-aim says so (`beyond correction`). Every measured voice also leaves an `Audio drift pane=` line at most every 30 s, each pane on its own throttle: the reference's carries the slew, and the others say `uncorrected`, since the slew does not follow them and their line is the only record of how far their sound is from their picture.

### Audio output and effects

`AppAudio.cpp` owns the sound's settings (`AudioSettings`, saved in `QCONFIG`): the output, the speakers, the volume's limit, the timing, the pitch, the language and the effects. The picture menu's Audio and Audio sync submenus, the keys and the settings window's Audio tab all act through it.

`AudioDevices` lists Windows' active render endpoints by name and its default multimedia one, and registers an `IMMNotificationClient` that only raises an atomic flag; Windows calls it on a thread of its own. The tick (`serviceAudioOutput`) reads the list again once the flag has been quiet for 250 ms, since a headset adds and removes several endpoints at once. The output wanted is the one chosen while it is listed, else Windows' default; an empty choice follows the default. When the output wanted is not the one open, or nothing is open, the output is reopened, and a chosen output that went away is named in a notice: its name is kept with its id, so it is still named, as not connected, while it is away, and the choice comes back into force when it does.

A reopen takes every pane's sound down and brings new voices up: each source's audio is disabled, `AudioOutput::reopen` destroys the voices, the mastering voice and the engine and creates them again on the endpoint's id (falling back to the default, which the log and the Audio tab say), each source is told the new layout (`setAudioOutputLayout`), and each pane's sound is sought again where its picture is, by the order in Threads and pause correctness (`reaimPaneAudio`), or, while the seek barrier waits, by rebuilding the barrier at the same target. A pane's audio-track change and its timing take the same path. Stereo is the default layout; "every speaker of the output" mixes the voices in the endpoint's own channel count and mask, and FFmpeg's resampler maps each file's layout to it. The resampler is built from a generation's first frame, and built again whenever a frame's channel layout, sample format or rate is not what it was built for -- a broadcast's AC-3 going between a 5.1 programme and a 2.0 advert, a 48 kHz recording joined to a 44.1 kHz one. At that change any first sound kept back goes out at the count, then the old resampler's filter delay is played out (`drainResampler`, which the end of the stream uses too), so the count stays on the stamps; the stamp follower and its learnt rate are kept, since its counts are 48 kHz output samples. A stream's first eight changes are logged (`Audio changes to <layout> at <rate> Hz; resampler built again`). Until 2026-10-26 the resampler was the first frame's for the whole generation: 5.1 to 2.0 crashed QuadDeck in libswresample, 2.0 to 5.1 lost the centre, the LFE and the surrounds until the next seek, and a change of rate played at the wrong pitch and speed.

The master volume runs from 0 to the limit chosen, a percent at a time from 100 to 200% (`clampAudioMaxVolume`). Up to 100% it is the mastering voice's volume; past it, the mastering voice stays at 1 and the excess is a gain in the effects. The effects are one in-place float XAPO on the mastering voice (`EffectsXapo`, running `AudioEffectsProcessor` from `AudioDsp.hpp`), so they act on the whole mix, in this order: the channels (stereo, swapped, left or right only, mono, voice removal), voice emphasis, a ten-band equalizer with a preamp (eighteen presets, or the bands by hand), a bs2b-style headphone crossfeed, stereo widening, night mode's compressor, the normalizer, the gain past 100%, and a limiter (`AudioLimiter`). Each stage switched off forgets all it held, so switching it on again starts as one never switched on: the equalizer's filter memory (a band at 0 dB, or past 0.45 of the rate, is left out of the run and its memory cleared, while a band that stays on keeps its memory across a gain change), the voice and crossfeed filters, night mode's envelope, and the normalizer's measured level, the gain it reached and the glide to it (`clearNormalizer`, which `resetEffects` shares). Until 2026-10-26 a band brought back from 0 dB first played a decaying burst at its own frequency from what its old memory held, a thump in the bass bands, and normalize switched on again played its first block at the gain it had reached before, up to +12 dB. The limiter looks 5 ms ahead: the gain each frame needs to stay under 0.98 is held as the least over that lookahead and 15 ms more, comes back over 100 ms, and reaches the samples through two moving averages that together span the lookahead, so no frame passes the ceiling and the gain never steps. The one before it acted on each sample as it came and let go over 50 ms, so past 100% it pulled each wave's top down and let go between them: a flattened top, a buzz on a loud low note, a click where it struck. It is always in the path, so turning the boost or an effect on or off never moves the sound in time: with nothing else to do and the mix under 0.98, once any gain it took has come back, the samples come out bit for bit, 5 ms late, and a hotter mix -- several panes at once, a hot master, a downmix -- is limited at any volume. `AudioOutput::outputLatency` counts the 5 ms with the engine's own latency. When XAudio2 hands the XAPO silence, what the delay still holds plays out over it; once only silence is left, passes are skipped as before and the gain is set back at rest, so the next sound is not met by a gain still coming back up. The window thread hands it new settings under a lock and a version count; the audio thread takes them at the start of a pass and never waits for the window, so a change written meanwhile is taken by the next pass. Taking them allocates nothing either: `AudioEffectsProcessor::configure` keeps the bands the equalizer runs in a fixed array with a count (`eqBands_`, `eqBandCount_`), and its clears are stores into fixed arrays and scalars, so neither `configure` nor a pass allocates. Until 2026-10-26 the band list was a vector filled again there, which could allocate up to seven times on the audio thread, each a possible wait on the heap's lock. If the effect chain cannot be set, the sound plays on without effects.

A pane's sound can be moved against its picture by every video's delay (saved) plus its own (cleared with its media, kept when the same video is opened again for a decoder, renderer or device change, swapped with its pane), at most ±10 s together. The decoder stamps its samples that much later (`setAudioDelay`), so the voice's timeline, the drift measurement and the re-aim all see the shifted time; the change is applied by seeking the pane's audio again. With pitch kept at another speed, the decoder time-stretches each audio generation (`TimeStretch`, WSOLA) at the tempo it started with (`AudioChunk::tempo`), and the voice plays it at the rate over that tempo, so the voice's span timeline still counts source time. A speed change sets the tempo before its seek; turning pitch keeping on or off seeks the panes not at 1×. The preferred audio language is handed to each open (`SourceOptions::audioLanguage`), where a track in that language comes before the default one; changing it switches the videos open to such a track where they have one.

## Session model

The player keeps a list of video sets instead of saving and opening sessions (2026-11-04). `VideoSets.hpp` is it, pure: a set is one to five videos by their place on the screen -- a file's path or an Emby locator, with the title its pane had and, for an Emby item, the server's name, the item's path on the server, its name, series, type, season, episode and year -- and its `LayoutMode` with the place shown larger; the list has a `PlayOrder` for what follows a set's end. `QSETS 1` is its text: `order`, then per set a `set` line (quoted name, layout, expanded place, count) and a `video` line per video, every text quoted; `readVideoSets` refuses anything but a whole document (another format, an old `QDECK` among them, a newer version, a set of none or more than five, a video without a path) and clamps the numbers. App keeps the list in `videosets.qsets` beside `settings.qconfig` (`App::videoSetsPath`), read in `run()` after the settings and written whole after each change through the transactional path below; a file there that cannot be read is never written over (`videoSetsReadOnly_`) and the face says so. It leaves the player only as a `.qdeck` file the viewer exports; `Import…`, the command line and a forwarded or dropped `.qdeck` add its sets (`appendVideoSets`, which skips a set whose videos the list has in the same places). Ctrl+S (`addVideoSet`, `captureVideoSet`) appends what plays without a dialog, named by its first title and how many more; Ctrl+O and the bar's `BarItem::Sets` (`toggleVideoSets`) show the sheet's second face, `videoSetsOpen_` (`buildVideoSetRows`, `AppVideoSets.cpp`): a pinned toolbar (add, import, export, the order's drop-down), a Buttons row per set with Play and its `⋯` menu (play, move up, move down, rename in a TextField row, `TextFieldId::VideoSetName`, delete), and a Note per video with what is wrong with it. The two keys keep their QCONFIG ids, `open-session` and `save-session`, so no settings version moved.

A set plays through `SessionState`: `playVideoSet` takes `captureSession()`, clears every pane's media, offsets, rate, pause, repeat and loops and the master loop, puts the set's videos in panes 0 onward in place order with its layout and expanded place, and hands it to `applySession`, which now keeps the shader running when it is the one asked for rather than compiling it, or prompting about a file that cannot be read, at every set; each Emby pane is then marked `fromBeginning` so its item's resume position is not taken. The list's mode is `videoSetPlaying()`: the set's index while every pane that holds something holds what the set opened there (`videoSetPanePaths_`), so a pane closed, or one that failed, does not end it, and anything else put in a pane does. While it holds, Previous and Next (`openAdjacentFile`, the bar's step buttons, which `transportBarLayout`'s `setSteps` shows for any number of videos) go to the set `videoSetStep` names, round the ends only under Repeat the list; and `finishVideoSet`, before `finishMasterTimeline` in the tick (which leaves a set alone), plays what `playOrderNextIndex` names once the set has ended: on one timeline where `masterTimelineEndAction` without Repeat all would act, on the panes' own timelines once each is at its end (`videoSetPaneEnded`; `embyFinishPane` holds a set's Emby pane at its end instead of following its queue). Nothing follows: the deck pauses at its end with a notice. A set with a video that cannot play is skipped whole, never played short (until 2026-11-04 such a video was left out and the others closed up). `playVideoSet` -- Play, Previous / Next, a set's end -- starts the list going afresh (`videoSetTried_` cleared but for the set stepped from, `videoSetDirection_` the step's way), and `openVideoSet` passes over, before anything opens, a set with an Emby item it cannot ask for: signed out, or a locator naming another server than the session's (a server's new address with the same id is the same server), which the face also says. Each set opened is a run (`videoSetRun_`). The first failure of a run once it has opened -- `embyResolveFailed` on a set's pane (`videoSetPaneFailed`, in place of that notice), a set pane's source with an error (`checkVideoSetSources`, not while the device is lost and every source may fail), an item gone and not found again -- keeps why (`videoSetFailure_`; the video's own reason goes to `videoSetFailures_`, which the face shows as `could not play: ...` until a set opens it again), and `finishVideoSet` at the next frame, playing or not, goes on (`skipVideoSet`) to the set `videoSetSkipTo` names: the next the way `videoSetStep` goes, never one tried, under Shuffle any not tried. The notice of the set that plays says what was skipped and why. With none left, a set asked for leaves the deck and the list's going as they were (`playVideoSet` returns false), while a skip or a set's end stops the deck where it is; a run fails once, so a failed source left in its pane is not skipped again. `checkVideoSets`, when the face opens, asks the server for the list's items by id (`emby::itemsByIdPath`, in `subtitleBatches` of 100) and for each file whether it exists, on a thread of its own; an item the server no longer lists, or one whose pane gets 400 or 404 for its item while a set plays (`videoSetItemGone`, which closes that pane and says so), is searched for by what the set kept (`emby::refindPath`) and taken from the reply only when `emby::refindMatch` finds the one at the same server path, or else the only one of its type and name (an episode of the same series, season and number; anything else of the same year when both say): every set's locator is then rewritten and the list saved, and a pane closed for it opened again from its start while its set still plays; not found, or with the server not answering, its set is skipped (`videoSetRefind`'s `done` is given why). `itemPath` asks for `Path` too, so a set added from a pane already knows its item's.

`Session.hpp` still holds the `QDECK` format, though the player no longer reads or writes it; `SessionState` is what `captureSession` and `applySession` pass. Until 2026-11-04 Ctrl+S saved and Ctrl+O loaded it through a file dialog. `Session.hpp` writes the platform-neutral `QDECK 6` text format. Version 6 adds the fifth pane; version 5 adds per-pane volume and mute; version 4 added the four Smart Vibrance Plus values; version 3 added the audio mask and per-pane auto-repeat. The reader remains backward compatible with `QDECK 1`–`QDECK 5`, promoting old single audio slots to a one-bit mask, supplying reference-default vibrance values, reading only four pane records from old files and leaving the fifth pane at safe defaults. It serializes global playback/render settings and the complete five-pane state. File parsing validates enum ranges, rates, zoom, shader parameters and loop boundaries before `App::applySession` recreates sources. The session stores paths rather than media content.

The separate `QSTYLE 3` format contains only visual state: dynamic layout, expanded pane, five per-pane view/zoom records, shader selection/path, Smart Vibrance Plus parameters and dock pinning. `QSTYLE 1` and `QSTYLE 2` remain readable; their fifth PaneView stays at the default. ## Decode and render paths

`ReadAheadCache` provides custom AVIO for UNC paths and drive letters that
Windows reports as remote. Detection and file opening run on a per-file worker,
never the HWND thread. The sheet's NAS switch (General tab) defaults on and applies to
subsequent opens; `QCONFIG` persists it, and a file from before the option
reads it as on. QDECK/QSTYLE formats and existing playback policy are unchanged.

Two independent AVIO cursors (video/audio) share immutable compressed 1 MiB
blocks and one overlapped Windows file handle. Foreground misses take priority
over speculative reads, with round-robin servicing of simultaneous audio/video
demands. The video cursor drives continuous read-ahead after stream discovery,
including while paused or blocked on the small decoded-frame queue. The target
is 30 source seconds from container bitrate (size/duration fallback), capped at
256 MiB per file; unknown bitrate uses 32 MiB. A global atomic reservation budget
caps resident plus in-flight block allocations at 1 GiB, and active files share
that capacity equally. Decoder surfaces, AVIO buffers and allocator overhead
are outside this payload limit. No claim of network-level bandwidth reservation
is made. First-packet preparation aims for 3 seconds and waits at most 5 seconds;
high bitrate, EOF and capacity shares can shorten that target. A seek cancels
old demand/overlapped reads, preserves reusable blocks, and prioritizes the new
byte position without repeating the startup delay after the first frame. A seek,
interrupt or miss on one cursor never cancels a block the other cursor is
waiting for; a seek or interrupt also keeps a read-ahead fetch that is still
inside the video window. Once the window is full the worker sleeps until a
cursor moves rather than polling, re-checking its share of the budget once a
second.

Metadata probing is demand-only to avoid prefetching at an index located at EOF.
Transient failed reads retry after 250 ms; demand waits fail after 15 seconds
instead of inventing EOF. A Windows read requests cancellation after 10 seconds.
Close marks the cache stopped before joining either decoder, wakes consumers,
and cancels synchronous open/metadata operations and overlapped reads. Buffers
and OVERLAPPED storage stay alive until kernel cancellation completes; a broken
network driver can still delay that completion. FILE_SHARE_READ excludes writers
and replacement while open, so existing cached blocks cannot silently mix with
new file contents. The same share mode refuses a file another process already
holds open for writing, such as a recording in progress; any failure of that
open therefore bypasses the cache, and FFmpeg's own share-everything open
either plays the file uncached or reports the real error. HTTP/other protocols
and local disks retain the original FFmpeg input path. Custom AVIO allocation/freeing is owned separately from
avformat_close_input, and cancelled AVIO error/EOF state is cleared for a new
seek. Existing generation gates still determine which decoded frames/PCM may
be submitted. Request publication and old-cache-read interruption share the
VideoSource state lock, so a late cancellation cannot hit the replacement seek.
A fatal video open/decode failure stops the background cache as well.

A damaged packet costs its picture or its sound, not the pane. Both workers pass a per-packet decode error over (`VideoSource::passOverDecodeError`, each worker with its own `DecodeErrors`): the packet is not sent again, and a receive error is asked again, at most 100 times in one call; running out of memory and `pushVideoFrame`'s failures stay fatal. A stream ends in an error only when it has given no frame since its decoder was opened, decoding began at the stream's start, and either 100 errors came in a row (for the sound, a run that also covers `kAudioDecodeErrorSeconds`, 10 s of the stream) or the stream ended after an error: `; 100 errors in a row and no frame decoded` (for the sound `; N errors in a row over S s and no frame decoded`, N at least 100, without the span where its packets have no times), `; no frame decoded before the end of the stream`. From a seek's target -- App's opening seek, a resume, a pane added to a running deck, a reopen after the device was lost and an audio track switch among them -- such a run or end first starts a look at the stream's start (`StartProbe`, in both workers), with nothing shown or heard. If a frame comes, the errors the look met are written out, then `A frame decodes from the start of the stream; the seek to X s goes on` (for the sound, `the sound from X s goes on`), and the seek is made again from its own target in the same generation, errors then passed over without bound; if none comes, the pane, or the audio generation in Error, ends as it would have from the start. A new seek replaces the look. The log writes the first error at once and then at most one line a second; the ones held back go into `N more decode errors passed over from A s up to B s, the last: ...`, written at a frame decoded a second after the last line, at a seek, at the look and at the frame the look finds (ahead of its line that has the seek go on), at the end of the stream, ahead of a decode error that ends the pane (for the sound, ahead of any `failGeneration`), and when the worker stops. Until 2026-10-26 the first decode error ended the video pane, its sound with it, until the file was opened again, or silenced the sound until the next seek.

The settings page shows approximate media seconds buffered and total MiB; the
title shows first-open preparation. Performance diagnostics include each source's
resident MiB, ahead seconds, hits, misses and retry counts. This is separate from physical NAS testing.

`DecodeMode::Automatic` prefers D3D11VA but accepts software frames. `Hardware` strictly requires D3D11 surfaces; `Software` bypasses hardware setup. The choice is the Video tab's, under the card, since decoding is the card's work (the Playback tab's until 2026-11-07). WARP has no D3D11VA, where `Hardware` would fail every open. So the choice applies (`decoderChoiceApplies`) only with WARP neither chosen nor the device built on it: otherwise every source opens in software whatever the choice (`sourceDecodeMode`) -- a WARP chosen that would not build, leaving the device on a card, included -- and the row is greyed, its hint saying why. The row is greyed exactly while choosing on it would change nothing; the stored choice comes back when it applies again. Until 2026-11-07 the row was greyed for WARP chosen only, and a change on it under a fallback to WARP reopened every video for nothing. The row's choice goes through `videoPanelAction` like the tab's others, which does nothing and says nothing for the mode already chosen.

Hardware `AVFrame` clones pin the decoder texture and array slice. A D3D11 Video Processor converts each surface directly to a per-slot BGRA texture. Most software frames are converted to BGRA at the size the pane actually displays: never magnified past 1:1, snapped to eighths so that dragging a window edge cannot recreate the converter on every pixel of movement, and capped at 3840 in either dimension. 1920×1080 survives only as the seed used before the first layout hint reaches the decoder. A minimized window keeps the layout it had (`WM_SIZE` skips `SIZE_MINIMIZED`), so its empty client never asks for a one-pixel pane, whose frames would come back blurred; while minimized, `tick` still takes and drops the frames but neither builds the overlay nor renders or presents, and the loop then runs on its timeout. They are uploaded with `UpdateSubresource`. Their BGRA buffers come from a pool per source (`BgraBufferPool`, up to a queue's worth plus the frames held): a frame let go gives its buffer back and the next frame of that size takes it, instead of a new zero-filled allocation whose pages then fault in under swscale (at 3840×2160 about 21 ms a frame down to 6 ms in a scratch measurement). The BGRA copy is still made for every software frame, even one the renderer then sends down the NV12 route below, because that route is chosen per frame and can change after decode; `uploadSoftwareFrame` refuses a frame that lacks its stride × height bytes rather than read past them. One eligible software path preserves 8-bit YUV420 SDR frames with BT.601/BT.709 metadata, uploads them as NV12 and sends them through the video processor, so RTX Video HDR can also work when the decoder returned CPU frames. Other software formats retain the BGRA path.

All paths converge on shader-resource views. A vertex-shader UV transform implements Fill cropping and 1×–4× centered zoom; viewport geometry implements Fit and Stretch. A replaceable `ps_4_0` shader performs final pixel processing. `ShaderCompat.hpp` translates common PotPlayer/MPC Direct3D 9 `.txt` forms (named `s0` sampler variants, `tex2D` family, `p0/p1/pPrev`, `COLOR`) into D3D11 HLSL. It parses balanced sampling-call arguments while masking comments and quoted text. Plain `tex2D` becomes `Texture2D.Sample`; lod/bias/project calls use small helpers that evaluate their coordinate argument once, preserving enclosing and nested expressions. Bare `TEXCOORD` becomes `TEXCOORD0`. A semantic is rewritten, and a `COLOR` semantic (which ps_4_0 refuses) marks a shader as legacy, only after a colon that can introduce one (`declarationColons`): a colon closing a `?` still open at its bracket depth in the statement, one after `case ...` or `default`, and `::` are skipped, so `x ? 1 - color : color` and a native shader's `default: color = ...` are left as written. Until 2026-10-13 any `: color` matched, which rewrote a ternary's branch to `SV_TARGET` and adapted such a native shader as legacy, adding a second t0 and b0. A 48-byte pixel constant buffer at b0 maps c0 to dimensions/counter/clock, c1 to inverse dimensions, and c2 to a safe temporal-state default. The complete stateless Smart Vibrance Plus preset uses a separate 16-byte b1 buffer for intensity, saturation pivot, gray pivot and gray sharpness, preserving the legacy b0 contract. The vertex shader writes `SV_POSITION` and the transformed UV over `TEXCOORD0`–`TEXCOORD3`, and D3D11 links it to the pixel shader by register and component, not by name. So `adaptPotPlayerShader` gives each definition of a legacy `main()` a `float4 qdPosition : SV_POSITION` first, unless its first input is a position already (a parameter, or a struct parameter's first member, with `SV_POSITION`, `VPOS` or `POSITION`); an overload with a parameter of a built-in type and no semantic is a helper and is left as written. `compilePixelShaderFile` then reflects what the compiled shader reads and checks it with `unfedShaderInput`: an input that is not read is not checked, and one that is read must be a float; `VPOS` and `POSITION` must start register 0; any other input must lie in registers 1-2, and one wider than a float must start where a `TEXCOORD` starts, so a vector that starts at `.y` or `.w` is refused while a single float there reads the coordinate's v; a read clip or cull distance is refused; the other system values are skipped, `SV_RenderTargetArrayIndex` and `SV_ViewportArrayIndex` too, though the vertex shader writes neither, since NVIDIA and Intel Arc drivers give 0 and only WARP gives `TEXCOORD2.x`'s bits. A refused file leaves the shader before it drawing, and its message says what its `main()` reads where and what it needs. A file is compiled with the position given (`MainPosition::Given`), then as written (`AsWritten`, for a position the lookup does not see, behind a macro or in a nested struct), then before any struct parameter (`BeforeStructs`, for a struct whose first definition is one an `#if 0` leaves out), and the first the vertex shader feeds is taken; the refusal is `Given`'s when that compiled, else `AsWritten`'s, never `BeforeStructs'`, so a compile error is the file's own, at its own columns. Until 2026-10-26 a `main()` taking only `TEXCOORD0`, the usual PotPlayer form, read the position's register as its coordinate and drew every pane as one colour on a card and a wrong picture on WARP; the copies over `TEXCOORD0`–`TEXCOORD3` added in 0.9 never fixed that. No hardware frame is read back to CPU.

Two NVIDIA RTX Video features ride on that video processor, both off by default and stored as device settings in `QCONFIG 7` (`rtxvideo`), not in a visual preset. They are private stream extensions the driver accepts through `VideoProcessorSetStreamExtension`; the GUIDs and version/method words in `D3DRenderer.cpp` are the ones mpv and MPC Video Renderer ship, cross-checked, since NVIDIA publishes no header. At device creation the renderer records the adapter (a null-adapter `D3D11CreateDevice` takes whichever GPU drives the primary display), and on an NVIDIA adapter builds a throwaway 1080p processor to ask the driver once whether it honours Super Resolution (the enable call succeeds) and RTX Video HDR (`VideoProcessorGetStreamExtension` answers non-zero). Every few seconds and on resize it also reads, for the output the window sits on, whether Windows has it in HDR mode (`IDXGIOutput6::GetDesc1` colour space) and its SDR white level (`DisplayConfigGetDeviceInfo`). The outputs are read through a DXGI factory of the renderer's own (`displayFactory_`, at first the device's): a factory keeps the outputs as they were when it was made, so once `IsCurrent()` says it is stale -- after a monitor change, a mode change or Windows HDR switched -- `refreshDisplayFactory` makes a new one and finds the device's adapter in it by the LUID recorded at device creation; only that adapter's outputs count, as before. `WM_DISPLAYCHANGE` makes the next frame look (`noteDisplayChange`). Until 2026-10-12 the device's own factory was read for the whole session, and HDR switched while playing was not followed. `videoEnhancementNote` in `Core.hpp` turns wanted-versus-available into the one line under the two toggles, pure.

Super Resolution needs the processor, not the sampler, to reach the pane's pixels. When the pane actually upscales, `presentationSize` may magnify the processor's intermediate (in sixteenths, still bounded at 3840); the extension is applied to each slot's processor when it is built. This also covers the eligible software NV12 path above. The request and code path do not establish visual Super Resolution quality or software-frame throughput. RTX Video HDR needs somewhere to write HDR: when it is wanted, the driver supports it and the display is in HDR mode, `applyOutputMode` moves the swap chain to `R10G10B10A2_UNORM` with `SetColorSpace1(RGB_FULL_G2084_NONE_P2020)` through `ResizeBuffers`, without touching the device the decoders share, and drops every slot so the processors are rebuilt with 10-bit PQ output views. Hardware PQ sources use their declared DXGI stream colour space; eligible software NV12 uses its retained SDR metadata and the TrueHDR extension. When TrueHDR is declined for an SDR frame, or an SDR software format bypasses the NV12 bridge, the BGRA frame is converted by a separate shader from G22/BT.709 to BT.2020/PQ at the display's SDR white level after selected effects. Native CPU HDR retains its previous software colour and tone-mapping limitations; this does not add native software HDR support. Direct2D cannot draw sRGB into a PQ back buffer -- white would be 10,000 nits -- so in PQ mode the painter is handed a transparent premultiplied BGRA layer instead and a shader pass linearises it, scales it to the display's SDR white level, PQ-encodes it and blends it over the video. Whatever the swap chain's mode, the replaceable pixel shader still runs; in PQ mode it sees PQ-encoded values. The built-in Vibrance preset handles those explicitly as described below; other presets and external shaders retain their existing behavior.

A picture's pixels need not be square. `VideoSource` reads the sample aspect ratio with `av_guess_sample_aspect_ratio` at open (the container's first -- Matroska's display size, MP4's `pasp` -- then the stream's) and with each decoded frame on both paths (`HardwareVideoFrame::pixelAspect`; `pixelAspectRatio` in `Core.hpp` takes 0:1 and a ratio outside 0.1-10 as square). `videoDisplayAspect()` is the picture's whole shape: at open the codec size times the open's ratio, and once `frameForTime` hands a frame out, that frame's own decoded size times its own ratio, so a broadcast going between 4:3 adverts and a 16:9 film, or from 1920x1080 to 1440x1080 at 4:3, is followed, and the size read at open is never paired with a later ratio. The intermediates keep the stored proportions (`presentationSize`, the processor, swscale); `render` takes each pane's viewport and UV crop from the pure `panePictureGeometry(cell, outputWidth, outputHeight, pixelAspect, mode, zoom)` with the frame's ratio, and the sampler stretches the texture; square pixels come out bit for bit as before. Until 2026-10-26 the ratio was not read: a 16:9 PAL DVD (720x576, pixels 64:45) was shown at 1.25:1, an NTSC one (720x480, 32:27) at 1.5:1 and HDV (1440x1080, 4:3) at 4:3.

The built-in Smart Vibrance Plus uses a per-draw 16-byte b2 buffer, separate
from the unchanged legacy b0 and four-slider b1. `SlotTexture::rtxHdrApplied`
records whether that processor accepted TrueHDR; the global enhancement status
only describes the last processor and cannot choose a pane's shader route.
`bindVibranceColorSpace` selects the old SDR algorithm for non-PQ textures,
HDR-aware enhancement for hardware PQ from an accepted SDR-to-HDR conversion,
and exact passthrough for native/other PQ. Failed shader compilation leaves the
previous selection intact. b2 is unbound for all other presets/custom shaders.
Slot invalidation, output changes and device recovery also reset this state.
A custom shader file that cannot be read at a start or a device rebuild
(`App::restoreShader`) stays the choice: `customShaderPath_` is kept and saved,
the preset runs meanwhile, `customShaderUnloaded_` puts a note on the Shader
page, and the next start or rebuild tries the file again. That path opens no
message box, since device recovery runs inside the frame loop's tick.

HDR Vibrance runs in the existing composition pass: ST 2084 decode to nits,
BT.2020 linear luminance Y (0.2627/0.6780/0.0593), and colour scaled along the
constant-Y gray axis before PQ encoding. Exposure-normalized colourfulness
controls saturation rolloff; Gray pivot/sharpness suppress near-gray noise
(unlike the original SDR response, which is retained verbatim). A heuristic
exposure mask ramps up from 0.01 to 1 nit and down from 203 to 1000 nits, and a
warm red-yellow mask halves the added gain at its centre; this is not skin
recognition or display calibration. Gain smoothly approaches the legal RGB
boundary along the same axis, avoiding independent channel clipping. Linear Y
is retained within shader floating-point accuracy, but channel peaks can rise;
the boundary is the BT.2020/PQ encoding range, not the monitor's actual gamut.
Intensity 1 returns the input exactly. No extra AI pass, CPU readback or saved
format change is introduced. The UI and subtitles are composited afterwards.
Software frames outside the eligible NV12 bridge keep the BGRA path; SDR-to-PQ
presentation uses the explicit conversion above rather than the processor's
TrueHDR conversion. Native CPU HDR retains its prior software colour and
tone-mapping limitations; HLG and Dolby Vision support are not added. Native PQ
passthrough here applies to built-in Vibrance, not a promise about arbitrary
external shaders.

PotPlayer's video output settings, as far as one D3D11 swap chain for every
pane allows (`VideoOutput.hpp`, pure; the Video

frames, and half output rate (one frame out per frame in); each frame then
says its own field order or progressive. The slot stays an interlaced one
through size and mode changes. Interlaced software frames take the NV12
bridge into the processor for the same reason (`SoftwareUpload::interlaced`,
sticky). Double-rate (field) output would need the processor's past frames
and a second presentation per frame; it is not done.

The scaler and the colour controls are one more pass, drawn only when needed
(`drawOutputPass`, `kOutputShader`): Bicubic (Catmull-Rom, 4x4 taps),
Lanczos (3 lobes, 6x6) or nearest neighbour through a point sampler at texel
centres, then brightness, contrast, saturation and hue on the BT.709 luma
and chroma, the gamma, and TV levels, the sums `videoColorAdjusted` does in
C++. A pane shown smaller than its picture (more than 1% per axis) stays
bilinear, since the kernels are not widened for minification. Colour and
levels apply only to SDR output; PQ is left alone. With a user shader active
(anything but the Normal preset's plain copy, `effectShaderActive_`), the
shader first runs at the picture's own size into a per-pane `R10G10B10A2`
texture (`runEffectsPass`, with the constants it has when drawing straight
to the window), and the output pass enlarges that; with nothing chosen the
shader draws straight to the window as before.

Fullscreen covers the chosen display's monitor while it is connected
(`fullscreenMonitor`, by Windows' device name), else the window's own; a DPI
or display change while fullscreen places it again (`placeFullscreen`).

## Emby, subtitles and audio tracks

### Independent Emby panes (Plan A)

`embyRequestPlay` distinguishes ordinary Play/Resume from Add. Ordinary play
uses the last explicitly selected storage pane (`embyTargetPane_`), displayed
as its current V number and media title. Pointer hover and browser focus do
not change that target or the audio mask. Add reserves the first empty pane,
counting paths and resolving requests as occupied. It clears only the new
pane's audio bit, and leaves the other selected audio voices alone. Successful
Add exits Solo so the additional pane is visible. The browser stays open and
can be closed or navigated without stopping any source.

Only a full five-pane deck opens `EmbyPendingPlay`: a copied item, queue,
account generation and every destination's path/media generation. The sheet
shows V number, title and cached Emby/local thumbnail for each replacement,
plus Cancel. Confirmation rechecks the account, duplicate playback and the
chosen destination identity before any playback mutation; cancellation only
discards the pending request and restores browser scroll. Movies and episodes
offer explicit Add-and-resume and Add-from-beginning actions when applicable.
List and tile Add regions have their own `PanelHitKind::Add` geometry.

Each `EmbyPane` owns `emby::PlaybackQueue` (items, cursor and originating page)
and server/user/account identity. Queue helpers in `EmbyPlayback.hpp` preserve
duplicate playlist-entry identity. A reply may extend the same page without
dropping or reordering existing entries; looking at another page cannot replace
that queue. Explicit sorting reorders only the selected playback target's queue.
The old shared `embyPlaylist_` no longer exists. Detail-season pagination uses
the same per-pane extension rule.

While an Emby video or a local browser-managed pane participates,
`activeSeekMode()` is Independent; the saved local `seekMode_` is unchanged
for mapping, repeat, audio and EOF. A separate, session-only
`browserSeekMode_` starts Independent and lets F5 link user-initiated seeks
without changing the per-pane timeline. A linked pane rail, bottom rail or
arrow key rebases every ready video's adjustment against one chosen source
time, then performs one fast seek. Before the first alignment the bottom rail
shows the selected pane's source time; afterward it shows the linked target,
so arrows continue past the end of a shorter selected video. The rail spans
the longest video duration. A resolving pane blocks alignment until ready;
a failed pane must be closed and a video with unknown duration cannot be
aligned. Videos shorter than the chosen time follow their own end or repeat
rule; an A-B loop can remap the clicked time. Multiple local files opened by hand
without a browser-managed queue retain the user's saved Linked/Independent mode.
Resume is a source-local offset under the unchanged master clock. Opening,
replacement, seeking or pausing one pane retires only its seek-barrier ticket
and audio generation, without re-seeking other panes. A new source inherits
global pause; a request finishing later cannot resume the deck. The first
source may start the otherwise empty clock, and Add is still muted. Because
the master clock runs on through every replacement, it says nothing about the
only F6 or Emby video: `barTimelinePane` (`SyncState.hpp`) names that pane,
and `App::barTime` gives the bottom rail and the window title its
source-local time and length, zero while it is still opening or resolving.
A drag on that rail moves the pane (`seekBarTimelinePane`): an F6 file through
the master clock when the target is reachable, so it still lands on a
keyframe, otherwise and for Emby by `seekPaneTo`. The arrow keys on the only
F6 file take the same path, clamped to its length. Multiple independent browser
panes omit the bottom time and seek rail because the master extent includes
elapsed time before those panes were added. The remaining controls are still
labelled All. Browser Linked restores the bottom rail with source seconds and
the longest video duration. Existing explicit global synchronization and
multi-audio controls remain available, as does automatic audio handoff.

`finishEmbyPanes` observes each pane's presentation time against container or
server duration, then `endHandled` latches before stopping/reporting that pane
and applying the shared PlayOrder to its own queue. Other panes keep playing.
A next item already open elsewhere is selected without opening another session;
the ended pane remains held, so a timer cannot repeatedly advance it. `seekPaneTo`
(Home, an arrow, a pane rail) and Stop release that hold short of the end, as
the linked alignment does; a pane the viewer paused stays paused. Unknown
duration without server runtime does not trigger speculative early advancement.
Reports are built from each pane's playback/media-source IDs and local time,
including muted playback. Browser and direct-locator opens deduplicate the same
server/user/item, with a second uniqueness check at report generation. Account
changes enqueue each old Emby pane's Stopped request under the old session before
closing it and invalidating callbacks; local panes are retained. No new account,
device identity or persisted format is introduced.

Movie and Series information pages are an optional layer over the browser,
implemented in `AppEmbyDetails.cpp`. An item opens that layer only when its
library is identified by the current server's Views as `movies` or `tvshows`.
Other item/library types and ambiguous provenance retain their original
behavior. The `Info pages` button on the library's toolbar (and its shows')
and F5's Emby library switches edit the same preference. Search records each responding
library and waits for all replies before enabling results; Continue watching
uses a known parent or a read-only Ancestors request matched uniquely to Views.

`EmbyLibraryPrefs.hpp` keys overrides by the opaque server ID and library ID,
not a display name, address or item type. Eligible libraries default on;
unknown types default off even if a stale override says on. `QCONFIG 13`
adds `embylibrarydetails <count>` and quoted
`embylibrarydetail "serverId" "libraryId" <0|1>` lines after `subtitles` and
before QSTYLE. Versions 1–12 load with no overrides. At most 256 pairs of
512-byte UTF-8 IDs are accepted; duplicate keys, invalid text or malformed
values reject the configuration transactionally. Serialization sorts the
pairs for stable output. No token, media position or server address is added.

`EmbyDetails` owns its detail item, season/episode lists, scroll, metadata
generation and child-request generation separately from the source browser.
Back restores the unchanged list and its scroll, including Random/search
order. Hidden detail cancellation restores only the Emby scroll slot. Account
changes retire details, image replies and provenance; callbacks verify their
generation before applying metadata or children. Refresh reloads seasons and
retains the selected season if it still exists. A failed request leaves a
Refresh/Retry route. TV children page in batches of 300, automatically up to
20000, with explicit Show more thereafter.

Viewing details never adopts a playback queue or reports progress. Ordinary

`Add from beginning` follow the placement rules above. Each destination pane keeps its own
captured source list and queue; a detail-season page may extend that pane's
queue as later pages arrive, without replacing another pane's queue. Resume
uses the fresh item reply's latest position, while From Beginning remains
explicit through that reply.

`PanelRowKind::MediaDetail` uses one shared geometry for painting and hit

paints a cover-cropped backdrop with a dark scrim, contains the full poster
and optional logo, and stacks the poster above text below 680 DIP. Synopsis
expansion changes the row height and scroll range. Missing optional values

keys distinguish Primary, Backdrop and Logo, image index, tag and width,

uses the documented path without a Fields query; the existing playback

and artwork uses the [typed image endpoint](https://dev.emby.media/reference/RestAPI/ImageService/getItemsByIdImagesByTypeByIndex.html).
Trailer, predicted end time and editing/download actions are
outside this information-page implementation.

The full-deck replacement explanation is an opt-in wrapped Note. DirectWrite

Movie/TV identity uses `emby::displayTitle` for playback titles and most

so its playback sequence is not cut off at the first page. Their order remains
the server's; pagination does not enable the library's sort/filter/flatten
controls on these pages. A season's SeriesId wins, then its ParentId, then the
current Series page; with none available, its own id still scopes an
`/Users/{user}/Items?ParentId=...&IncludeItemTypes=Episode` request, ordered by
the core [IndexNumber, then SortName](https://dev.emby.media/reference/pluginapi/MediaBrowser.Model.Querying.ItemSortBy.html)
sort keys rather than alphabetizing episode titles. The season
therefore remains browsable without inventing an unrelated parent. The
official [Seasons](https://dev.emby.media/reference/RestAPI/TvShowsService/getShowsByIdSeasons.html)
and [Episodes](https://dev.emby.media/reference/RestAPI/TvShowsService/getShowsByIdEpisodes.html)
contracts document Fields and paging. Hierarchy requests do not automatically
expand a playing sequence across seasons.

The latest item reply remains authoritative for resume, including a nonzero
position accompanying `Played=true` during a rewatch. The existing five-second
start/end thresholds and Home-to-restart interaction are retained; this work
does not infer a new restart policy from the completed flag. Reports and server
writes during normal user playback remain on the existing path.

Emby is a source of items, not a second player. `EmbyApi.hpp` is the protocol, pure: request paths and queries, the reply shapes (`Item`, `MediaSource`, `MediaStream`, `PlaybackInfo`), report bodies, the `emby://<serverId>/<itemId>` locator a pane path holds in place of a file, and the `QEMBY 1` sign-in file. `EmbyClient` does HTTP with WinHTTP on one worker thread and queues each reply with its handler; `pump()`, called from `tick()` every frame, runs the handlers on the window thread, so nothing App owns is touched from the worker. Every handler carries a serial -- `embyRequestSerial_` for the browser, `EmbyPane::serial` for a pane -- and does nothing when the browser has moved on or the pane was reused since the request was queued. The token is stored under DPAPI in `%LOCALAPPDATA%\QuadDeck\emby.qauth`, separate from `settings.qconfig`, and travels to the server only as the `X-Emby-Token` request header, also for the stream FFmpeg opens: `VideoSource::open` takes `SourceOptions` whose headers become FFmpeg's `headers` option, so the URL that reaches `QuadDeck.log` and a `.qdeck` file carries no secret.

`MediaInput.hpp` owns authenticated media transport for both `VideoSource`
demuxers, including photos. Before opening a credentialed HTTP(S) URL it checks
that the loaded FFmpeg protocol supports `max_redirects=0`, then applies that
option to the connection. Redirects on initial open, Range seeks and reconnects
are refused, including same-origin redirects. The initial `io_open` allows the
original URL once, then refuses secondary demuxer resources (for example HLS
segments). Static Emby media is a direct file; local/NAS inputs with no headers
keep their existing transport. No URL preflight is used as an authorization check.
A connect or read that receives nothing for 15 s (`kHttpReadTimeout`, FFmpeg's
`rw_timeout`) fails, so a server that goes silent without closing the
connection no longer holds the pane frozen: the reconnect options resume at the
same offset, or give up after their 0, 1 and 3 s delays (an open or seek against
a server gone for good fails after about a minute). Before 2026-10-13 there was
no timeout and such a read waited for good.

Embedded text has one conservative retention budget across a source's readers:
64 MiB and 200,000 accepted rectangles, including deduplication keys, libass
events, fallback cues and lookup metadata. A bounded temporary key rejects
duplicates before charging a new rectangle for parsing and retention; decoder
packets are limited to 1 MiB and headers/rectangle text to 256 KiB. Source
saturation stops later subtitle decoding, while an oversized
stream stops only that reader. Existing lines and deduplication survive seeks;
close/reopen clears the cache and budget. These limits bound application-owned
retention, not third-party decoder/libass allocations or total process memory.

Both plain markup extraction and SRT/WebVTT-to-ASS conversion scan angle
delimiters monotonically, cache closing-brace searches and limit entity lookahead
to eight characters. An unclosed or unknown tag cannot cause repeated suffix
scans or repeated copies of a large candidate. Malformed nested angle openers
begin new candidates; normal ASS overrides, font tags and entity semantics remain.
These bounds apply independently of the worker-thread parsing and window-thread
libass rendering described below.

Subtitles are drawn by libass (`AssSubtitles.*`, vcpkg `libass` with FreeType, HarfBuzz and FriBidi, DirectWrite as its font provider): a script as it is written -- positions and movement, the faces it names and those the video brought, colours, outlines, shadows, blur, rotation, fades, clips, drawings, karaoke. One `AssSubtitles` per pane and per video's media (`App::assPanes_`, made again when `subtitleSerial_` changes, moved by `swapPanes`, dropped by `resetPaneMediaState` -- on every reopen, the same video's too, since libass counts the old source's embedded events -- and when the pane has no source) holds a libass library with the video's fonts, a renderer and the script shown; it is used on the window thread only. `App::syncAssSubtitles` brings it up to what the pane shows each frame: a file's or a server's stream's text (`SubtitleTrack::text`, kept by `parseSubtitles` beside the cues) loaded whole -- an ASS or SSA script as it is, an SRT or WebVTT file through the pure `plainSubtitleScript`, which turns its cues into events of one style (`plainSubtitleHeader`: 384x288 like FFmpeg's stand-in, so the sizes a stream's decoder writes for `<font size>` hold; white, a black outline, the face of the most wanted language from `plainSubtitleFont`, libass's box style 4 when `SubtitleSettings::background` asks for one) and its HTML-like tags into overrides (`assTextFromSrt`: only the tags SRT and WebVTT have count, so "a<b and c>d" stays text, and a backslash before n or h stays a backslash) -- or, for a stream inside the file, the stream's header and then its events as the video worker reads them, each handed over once. A plain script is made again when its look changes. The fonts a video brought (`VideoSource::fonts`) are added once the source is ready; libass's font lookup is begun again then (`addFonts`), because it keeps the stand-in it already chose for a name. `App::renderAssSubtitles` takes its frame from the pure `subtitlePlacement` (AssSubtitles.hpp). A script's frame is the picture as it is on screen (`visiblePictureRect`: Fit's fitted rectangle, the cell for Fill and Stretch, which a zoom does not move), with the whole picture (`pictureRect`: Fit, Fill, Stretch and the zoom as the renderer draws them) given against it as margins -- negative where Fill or a zoom crops -- so a script's coordinates are the picture's and nothing it draws lands on Fit's bars. The rectangles take `storedPixelAspect(videoWidth, videoHeight, videoDisplayAspect)`, the pixel aspect against the size read at open, which libass keeps as its storage size, so the pixel aspect libass derives from frame and storage agrees with them: a DVD's lines stretch 64:45 as in VSFilter, and a broadcast gone from 1920x1080 to 1440x1080 at 4:3 keeps square glyphs. The storage size stays the one read at open after the picture changes size, so blur and 3D transforms are measured against the old size, and after it changes shape (an HD 16:9 programme to a 720x576 4:3 advert) the pixel aspect libass works out is the new shape over the old one, and the glyphs are squeezed or stretched; that case is not corrected yet. Where the picture is cropped, its unplaced speech is laid out in the frame instead (`ass_set_use_margins`), or it would fall off the pane; what the script places still goes with the picture. A plain script's frame is the whole cell with no picture in it and no storage size: its lines are sized and placed against the pane, bars included, never stretched, as the plain lines always were and as mpv sizes converted subtitles by its window. `SubtitleSettings::size` is libass's font scale, applied only to lines the script does not place (`ASS_OVERRIDE_BIT_SELECTIVE_FONT_SCALE`); `SubtitleSettings::position` is libass's line position, how far the bottom lines are raised above their style's place, and the transport bar and the pane's strip add to it while they are up (`paneSubtitleClearance`: the bar's settled height from half its slide, the strip's from half its fade; the "All" capsule counts only in the panes it is over, and as the higher of it and the strip, not their sum, and the line position rounded to a tenth of a percent: every change empties libass's caches; lines drawn without libass follow both as they move). Colours are corrected from the script's `YCbCr Matrix` to the video's (`subtitleColourForVideo`, `VideoSource::colourMatrix`), as xy-VSFilter's successors do; a script that names none is taken as BT.601. The video's is the matrix and range the picture is decoded with (`videoColourMatrix` through `videoColorMatrixFor` and `videoColorFullRange` in `ColorConversion.hpp`): an untagged stream by the decode paths' size rule, SMPTE 240M and FCC as untagged, RGB, BT.2020 and ICtCp left uncorrected; until 2026-10-13 it used a size rule of its own (BT.709 from 1280 wide) and named 240M and FCC, which no decode path converts with. What libass hands back -- coverage masks in one colour each -- is composited into premultiplied BGRA pieces, one per place on the pane that has lines (overlapping masks merged), so that a sign in a corner and the speech at the bottom are not one picture the size of the pane to clear and upload; the same picture comes back while libass reports no change. The scene carries it (`OverlayPaneScene::subtitleImage`) and `Overlay::drawSubtitleImage` draws each piece pixel for pixel before the chrome, keeping a bitmap per piece and refilling it in place while its size holds. A style's first appearance loads its face. Where libass cannot be set up or reads no event from a script, the cues are drawn as before: `Subtitles.hpp` parses SRT, WebVTT and ASS/SSA into cues with tags and overrides stripped and of a line's placement only whether it belongs at the top (`SubtitleCue::top`, from `\an`, SSA's `\a`, `\pos`/`\move` against `PlayResY`, a style's alignment, an SRT's `{\an8}`), drawings dropped, a layered line once (`subtitleLinesAt`); `Overlay::drawSubtitle` paints them as white letters with an eight-way black outline, a box where `background` asks, the size a share of the pane's height, the bottom lines 6 % plus `position` above the edge or clear of the bar, in the face DirectWrite substitutes for the most wanted language (`App::subtitleLocale`).

A pane's subtitles come from one of three places, `App::SubtitleKind` (`AppSubtitles.cpp`). `EmbyStream`: a text stream of an Emby item that is not read with the video -- a file beside the video on the server's disk, or one inside it that the source turned out not to read -- fetched whole from `/Videos/{id}/{source}/Subtitles/{index}/Stream.{ass|srt}` -- as ASS when that is the stream's own format (`emby::isAssSubtitleCodec`), which keeps the placement the conversion loses, and as SRT otherwise or when the ASS request fails or parses to nothing; the request goes through a client of its own (`embySubtitles_`), as pictures do, because extracting a stream can take time, and neither a click in the browser nor a progress report should wait behind that. `File`: a file beside a local video (`name.srt`, `name.xx.ass`, ssa, vtt) or one loaded by hand (the menu, Alt+O, a drop on the pane), read as UTF-8 (one that starts with a UTF-8 BOM even past a stray bad byte, `isUtf8Text`), UTF-16 with a BOM or the system code page. `Embedded`: a text stream inside the container, a local file's or an Emby item's. Fetching embedded subtitles separately can delay external subtitle requests while the server extracts a stream. The stream URL hands the file over unchanged (`Static=true`), so its streams are read as a local file's are: `App::subtitleOptions` offers a server stream that is not external and is text as `Embedded` (`embyStreamReadWithVideo`), trusting the server's index -- the server numbers a file's streams as FFmpeg does -- until the source is open, and then as far as the source has a reader for it; `adoptEmbeddedSubtitles` turns a shown stream the source does not read after all into an `EmbyStream` request for the same index. The first two are parsed whole into an immutable `SubtitleTrack` held in `subtitles_`. A script has lines when it has a cue or a `Dialogue` event whose times read (`SubtitleTrack::events`, `hasLines`): a script of signs drawn as shapes leaves no cue but is libass's to draw, so it is neither a file without lines nor an ASS stream to ask for again as SRT. Its `Events` field names are matched in any case, as libass matches them. Nothing is read on the window thread: `loadSidecarSubtitles` and `loadSubtitleFile` list, read (bounded at 16 MiB before the read) and parse on a detached thread and post the result through `MainThreadQueue`, where it finds its pane by `subtitleSerial_` -- a number unique across panes, moved by `swapPanes` and retired by `resetPaneMediaState` -- and is dropped when the pane has moved on or another choice was made meanwhile. An Emby stream's reply is held to the same 16 MiB (`kSubtitleByteLimit`) by its client, which stops reading there (`EmbyClient::setBodyLimit`, `Response::tooLarge`); `embySubtitleArrived` answers a 401 or a failure on the window thread and moves a body to a detached thread for `readSubtitleReply` (decode, the UTF-8 check for ASS, parse), whose result `embySubtitleRead` takes back on the window thread only while `embySubtitleWanted` still finds the pane by serial, the same stream and the same choice -- the ASS-to-SRT retry and the notices included. libass still loads the script on the window thread.

Embedded streams are read by the video worker, not a second time. `SourceOptions::readSubtitles` (set for local files by `App::localSourceOptions` and for an Emby item's stream by `embyStartResolved`; not for a photo) has `VideoSource::openSubtitleDecoders` open a decoder for every text subtitle stream (`AV_CODEC_PROP_TEXT_SUB`) and leave those streams undiscarded on the video demuxer; `decodeSubtitlePacket` turns each packet's ASS event (`cueFromDecodedAss`, under the header `parseAssHeader` read from the decoder) into a cue and `insertSubtitleCue` adds it to that stream's track, in order and once -- a seek back passes the same packets again. The tracks live under `subtitleMutex_`; `subtitleLinesAt` answers for the stream `setSubtitleTrack` named, so a change of stream is a change of which track is asked and shows at once. A Matroska file keeps a line in the cluster of its first moment, so a seek that starts reading at a keyframe would never see the line being spoken there: `handleVideoSeek`, when there are subtitle readers and the container is Matroska, looks the landing keyframe up in the stream's index and seeks again to a little before it (`kSubtitlePrerollSeconds`, fewer in a high-bitrate file so that at most about 24 MiB is read, never under two), and the read loop passes video packets over until that keyframe (`videoSkipToKeyframe_`). A scan of the whole file for its subtitles was considered and not done: Matroska's demuxer reads every block to skip it, which on a share is the whole file. Streams of pictures (PGS, VobSub) are listed by `subtitleTracks` with `text` false and offered greyed. For libass the same packets are kept as events as well (`SubtitleEvent`, `subtitleEventsSince`), with the decoder's header (`subtitleStreamHeader`): an ASS or SSA stream's own, which `syncAssSubtitles` passes on, or FFmpeg's stand-in for any other text stream, which is replaced by the plain header so that a SubRip stream inside a file looks like an SRT beside it; so is an ASS stream that came without its header, whose events libass would otherwise drop for want of a format line. An event is kept once, by its times and its text and, for an ASS or SSA stream, its read order (a script may write a line twice on purpose); a plain stream's events get read orders of the source's own, because its decoder counts from 0 again after every seek and libass drops an event whose read order it has seen. Lines arrive as the demuxer reaches them, so a file whose subtitle packets were not interleaved with the video (all of them late in the file) shows them only when playback gets there. `openVideoInput` also collects the container's font attachments (by codec, MIME type or name; at most 256 MiB) for every source, a server's stream included, and the matrix the video's colours are decoded with.

What is shown when the viewer has not chosen is `App::autoChooseSubtitle` and the pure `chooseSubtitle`/`rankSubtitles`: the stream the Emby server names in `DefaultSubtitleStreamIndex` (whether the server or the video hands it over), where it names one -- an account whose subtitle mode is `Smart` with no language names none for anything, which is why this exists -- and otherwise the candidate that suits the wanted languages best. `subtitleLanguageTag` reads a language from a container's or the server's code and, failing that, from a title or a file name's suffix (`chs`, `SC`, `unibig5`, a name in its own script); `subtitleLanguagePreference` is the viewer's choice (`SubtitleSettings::language`) before Windows' own language list, the languages other than English first; `subtitleLanguageRank` orders exact script, same language, a file naming no language, the next wanted language, a stream naming none, and anything else. A local file's sidecars are ranked on the scan's thread (`scanSidecars`), its embedded streams by `SourceOptions::chooseSubtitle` on the decoder's thread the moment the container's streams are known, and `adoptEmbeddedSubtitles` (from `tick()`) takes the source's choice up once it is ready unless a file beside the video is already shown. An Emby item's streams are ranked as one list, those the video carries with those the server hands over, as they were when the server handed them all over. A choice at the menu, the keys or the sheet sets `subtitleChosenByViewer_`, after which nothing found later chooses for that pane; a subtitle so chosen (not Off) also shows that video's lines (its bit of `SubtitleSettings::shown`), the menu having no switch of its own. A reopen of the same video keeps that choice and the read marks: the local branch puts the held files back after `loadSidecarSubtitles` and calls `selectSubtitle(..., false)` on the new source, and `embyStartResolved` does the same instead of `autoChooseSubtitle` (the server's default); the player's own choice is cleared and made again, so an Emby pane asks the server for its stream on the new `EmbyPane`. Each video has its own switch -- the Subtitles button on its strip, the bar's for the only video, a switch in its rows on the settings window's Subtitles tab, and Alt+H for the video the keys act on (`toggleSubtitles(pane)`) -- which hides and shows that video's lines alone through its bit, keeps its choice and says whose (`V2 subtitles hidden`); the bits are a pane's as its repeat and volume are, saved, and traded by `swapPanes` with the videos (until 2026-10-19 one flag, `SubtitleSettings::show`, hid every video's). Turned on for a video with nothing chosen, a switch chooses as the player would have (`preferredSubtitle`, which `autoChooseSubtitle` applies only while the viewer has not chosen), or say the video has none, or, for an Emby item still being resolved, that it is still opening (below). `readSubtitleFile` says what a file came to (`SubtitleRead`), and `subtitleFilesFailed_` keeps it per pane, the scan's findings included even when the viewer has chosen: a file without lines or over the limit is listed greyed, `(no lines)` or `(too large)`; one that could not be read, as a share that hiccupped, stays on the menu, `(could not be read)`, but out of `autoChooseSubtitle` and Alt+L, so neither comes back to it over and over; a read that succeeds later clears the mark. The keys are PotPlayer's (read from its own language file): Alt+H, Alt+L, Alt+O, `.` `,` `/`, Alt+PgUp/PgDn, Alt+Up/Down/Home -- Alt keys arrive as `WM_SYSKEYDOWN` with bit 29 set and are routed by `handleAltKey`, their `WM_SYSCHAR` swallowed. The Subtitles menu (`appendSubtitleMenu`: Off, the options, next, load, timing) is shared by the pane menu and the right-click on `BarItem::Subtitles`. The player runs under an open menu and a video's end may open the next one in the pane, so the menu keeps its entries, and the pane menu its audio tracks' stream indexes (`appendAudioTrackMenu`), with the pane's `subtitleSerial_` when built -- a number that changes only with the pane's media, `loadSidecarSubtitles` being called only from `openSource` just after `resetPaneMediaState`, and kept when the same video is opened again for a decoder, renderer or card change or a device recovery, so an open menu, the Load dialog, a waiting folder step and a replacement prompt still find their video. An answer that comes while that video has no source is kept or said: `selectAudioTrack` records the track for the next source, and for an Emby item still being resolved the Load entry and the Load dialog's file show `The video is still opening; open its subtitles again once it plays`, as `openExternalSubtitle` does. Next subtitle (`cycleSubtitle`, the menu's and the key's), and a video's subtitle switch turned on with nothing chosen (`toggleSubtitles`: Alt+H, the pane's chip, the bar's Subtitles button, the settings window's row), refuse with that notice whenever the pane has no source and `paneOpening` is true, whether or not the device is being rebuilt: every pane with a path reads as loaded then, but a fresh `EmbyPane` has no streams to step through or choose from; a pane waiting for the device keeps its `EmbyPane` and its streams, is not resolving, and steps and switches. The open menu's `choose` holds them (`PaneMenuSnapshot`: taken as it opens and put back only for its command, so a key or another menu meanwhile goes by what the pane offers now); `menuCommandPane` sends a command to the pane now holding that serial, after a swap too, and drops it with a notice when the video has gone. An audio entry selects the stream it listed, not the one now in its place. `SubtitleSettings` (show, language, size, position, background; `Core.hpp`) is the `subtitles` line, five words since `QCONFIG 12`; a `QCONFIG 11`, which drew the box behind every line and had no word for it, is read as without the box, and older files as shown, automatic, default size and place. Before `QCONFIG 14` the position was every bottom line's height above the pane's edge; such a value is dropped to 0, the script's own place, when it is read.

Parsed subtitle tracks keep a prefix-maximum end-time index alongside their start-sorted cues. A query first finds the cues that have started, then skips only a prefix whose cues have all ended and filters the rest with start-inclusive/end-exclusive boundaries. This preserves long-lived signs beneath arbitrarily many short dialogue cues and works equally after forward or backward seeks. The index is built once before the track becomes shared and immutable for playback; manually constructed tracks without an index use a complete scan of the started cues.

Audio tracks: `VideoSource` lists the container's audio streams when the video input opens, `setAudioTrack` names one by stream index, and the audio worker honours it when it opens and, for a running source, on its next seek -- the demuxer is repositioned anyway, so the decoder is swapped first (`openAudioCodec`), discards updated, and the timeline reset as for any seek. `App::selectAudioTrack` follows the request with the same audio-only relocation an output change makes, or rebuilds the seek barrier when one is active. It records the stream in `audioTrackChoices_`, also while the pane has a path but no source yet; `retireSource` refreshes it from `requestedAudioTrack`, `swapPanes` swaps it and `resetPaneMediaState` clears it with new media, and `startSourceStream` starts the next source on it in place of the caller's stream, leaving `SourceOptions::audioLanguage` empty then, since `openAudioInput` lets the language go ahead of a requested track.

## The local folder as the list, and Explorer's file types

One local video brings its folder with it. `openSource`, when the pane it opened is the only one taken, calls `localFollowVideo` (`AppLocal.cpp`), which lists its folder through `refreshLocalList` and `listLocalFolder` unless the list already shows it (below): the folder is listed on a detached thread (`scanLocalFolder`: media files by `kVideoExtensions`, with size and write time, in Explorer's order by `StrCmpLogicalW`; `markSubtitleFiles` notes each video that a subtitle file of the folder fits by `subtitleNameFitsVideo`, every video it fits rather than `videoForSubtitle`'s longest, because that is what `scanSidecars` loads when the video plays) and arrives through `MainThreadQueue` under a serial, as sidecar subtitles do, because a share that has gone away must not freeze the window thread; the same folder is not read twice unless `Refresh` forces it. `localEntries_` is the listing as read, `localList_` the listing ordered by the browser's sort key with the pure `orderLocalEntries` (`LocalPlaylist.hpp`: size or date on top of the name order, reversed on request, one shuffle per folder and session for random; length and the other keys a folder cannot answer stay by name). `siblingFiles` supplies the visible listing as a fallback only for manually opened local sources without a browser-managed pane queue; queued browser sources follow their pane snapshot. It never reads a folder itself. A manual pane whose folder is not the one F6 shows has it read when it opens (`requestSiblingFolder`, a detached `scanLocalFolder` posted back under a serial to `applySiblingFolder`) into `siblingFolders_`, kept as read and ordered by the sort in force each time it is walked, one entry per folder some pane is in; giving such a pane a `localPanes_` queue instead would make it `PaneOrigin::LocalBrowser` and put a linked deck on per-pane timelines. A step key or the only video's end that finds its folder unread (or read empty) asks for it, says `Reading the folder…`, and leaves a `PendingFolderStep` keyed by the video's media serial, which follows it through a swap; presses made meanwhile add up. `runPendingFolderStep`, run when any folder listing arrives, drops it when that video is no longer there, steps when the press is under `kFolderStepWaitMs` (1.5 s) old, and goes on from an end only while the deck is still that one shared video, paused at its end (`finishSingleVideo` paused it, so the master end check is quiet meanwhile), with a play order that goes on. A step waiting for F6's own scan of the same folder does not start a second read, and a folder that comes back empty says `The folder could not be read`. The same thread then reads each file's length and whether a text subtitle stream is inside (`probeLocalFile`: FFmpeg opens the container, and looks two megabytes further only when opening did not say a length; a stream counts by `VideoSource`'s rule, text with a decoder, so pictures such as PGS do not; an interrupt callback ends it when the scan is superseded or the player is gone, through `ScanToken`) and posts them a few at a time to `applyLocalProbes`; what was read is kept by path in `localProbes_` with the size and write time the file was listed at, so a refresh reads again only a file whose size or date changed since (a download or a copy that finished) and, when forced, one that did not open (`LocalProbe::opened`); until then a changed file shows no length rather than its old one (`localProbeCurrent`). `buildLocalRows` tags a video with either kind of subtitles (`localHasSubtitles`) `Sub`: `PanelRow::tag` on a list row, drawn before the value, `tileTags` on a tile, at the picture's bottom-left. By length a file whose length is not read yet sorts last, whichever way the rest run, and takes its place when it arrives.

The list moves between folders. Read with its folders (`scanLocalFolder` with `folders`: those Explorer shows, not hidden or system, so a drive's recycle bin stays out), a folder lists its subfolders ahead of its videos (`localFolders_`, by `StrCmpLogicalW`) as rows of their own, named by params counting down from `kLocalFolderParam` (-2; -1 names no row), so a video's param stays its place in `localList_`; a folder row's value is `›`, its tile has no picture (the shell's would be an icon, or a slow look inside a share's folder) and the badge `Folder`, and neither takes an Add. Choosing one lists it (`localOpenFolder`); the navigation row's `↑ Up` lists `localParentFolder`, which stops at a drive's top (`D:`, as a file's folder is spelled, read as `D:\` by `localListingPath`) and at a share's (`\\nas\share`), where the button is not shown. The header is `localFolderCrumb`. The arrangement is `EmbyBrowserPrefs::flat`, shared with the Emby browser's All videos as the view and the sort are; the toolbar's third button, `All videos`, switches it at once and is lit while it is on, as its first, `Thumbnails`, does the view (`localToolbarAction`, `localSetFlat`), and also retires a hidden Emby page that takes it (`embyRetireHiddenList`, split out of `embySetSort`), so that page asks for the choice when it next shows. All videos (`scanLocalListing`, flat) is every video under the folder and no folders, walked depth first -- each folder's own videos, then those of the folders in it -- by name; it does not go into a junction or a symbolic link (`IsReparseTagNameSurrogate`), stops at `kLocalFlatDepth` (16) folders deep and at `kLocalFlatLimit` (5000) videos, which the list says (`localListCapped_`), leaves out a folder that cannot be read rather than failing, and ends when its scan is superseded, checking the token between folders. Any listing leaves out an entry whose type cannot be read -- a junction or symbolic link whose target is gone or out of reach, an entry access to is refused -- rather than failing the folder; only an error of the directory iterator itself fails a listing, which a partial listing must not become a queue on. Until 2026-10-26 one such link (a junction to an unplugged drive, a link to a sleeping NAS) failed its whole folder: F6, the steps, Explorer's queue and the subtitle search found nothing there, and All videos left out every folder holding one, with everything under it. Subtitle files are matched within each folder, as `scanSidecars` loads them. A video in a folder further in is labelled with that folder after its name (`localRelativeFolder`), so a narrow dock still shows the name; where that cuts the folder off, the row's `hint` (the sheet's tooltip) is the folder and name. Such a list can hold one name in two of its folders, so `localEntryIndex` takes the file of the path's own folder before the first of its name. `localListCovers` -- the file's folder is the one shown, or with All videos one it is under -- is what the playing marks, `siblingFiles` and the legacy adoption ask; `localListHolds` adds that the file is listed, and is what Explorer's added file and the adoption copy the list on. The list therefore no longer always shows the target's folder: `localFollowVideo` (`openLocalList`, and `openSource` for the only video) moves it there unless it already holds that video or the video is the one it last followed (`localFollowedPath_`), so a folder the viewer went to stays when the sheet closes by the edge and comes back, and a subfolder's video chosen from All videos does not narrow the list to that subfolder. `listLocalFolder` reads the folder shown again only when forced, when it was read with nothing in it, or for the other arrangement (`localListRequestFlat_`; `localListFlat_` is that of the list shown, set when it arrives); another folder or the other arrangement starts from its top.

The sheet keeps its place. Settings, the Emby browser and the folder list each have a slot (`sheetScrollSlot`); `rememberSheetScroll` stores the scroll when the sheet closes or changes what it shows and `restoreSheetScroll` brings the slot of what it shows next, so F6 reopens a list where it was left. Reopening the Emby browser keeps the page shown and asks for it again in place (`embyRequestPage(0, true)`: nothing emptied, no "Loading" row, the whole list shown asked for rather than its first page; populated Random pages and search results are left as they are, using the same keepsOrder rule as automatic refresh; an outstanding initial, further-page or refresh request is not superseded by reopening). Choosing Random again explicitly requests another shuffle. A sort chosen while the Emby sheet is hidden retires the old browser serial and clears its cached list and request flags, so the next open fetches that choice once; it neither requests a hidden playlist nor resets another sheet's scroll. A browser that stays up keeps itself fresh the same way, because what was watched, added or renamed on the server -- in another client, or by this player's own reports -- shows only when the page is asked for again: `emby::listRefreshDue` (pure) says when, from an `emby::ListRefreshState` that `embyRefreshState` fills and `embyTick` asks every frame (`embyRefreshWhenDue`). It is due when there is news (`embyWantRefresh`: `WM_ACTIVATE` bringing the window back to the front, a Playing or Stopped report sent -- the request goes out behind the report on the same queue) and every thirty seconds the browser is up; never while a press or a drag is under way or a request for the page is out (`embyRefreshing_`, which also keeps `embyLoadMoreNearEnd` from overtaking it with a newer serial), not within two seconds of the last asking, not for a page never asked for, and not where asking again would not keep the order -- a random order, a merged search. A list grown past 2000 items is asked for again on news only. Such a request is quiet (`embyRefreshQuiet_`): its failure is logged and the list left alone, and the log says once for a page that it is kept fresh and afterwards only when `emby::sameListing` finds the reply differs. The `Refresh` button of the navigation row (`embyRefreshShown`) asks at the viewer's word, runs a search again, and has `ThumbnailCache::forgetFailures` drop the pictures that failed so they are tried once more. A reply that replaces the list under a press gives the press up when the row pressed has come to name another item (`embyPressedItem`, `embyKeepPressOn`), since a row's param is its place in the list. And a page asked for again in place becomes a pane's list being played only through `emby::adoptQueue` (`EmbyPlayback.hpp`) and the queue rule under "Independent Emby panes": the same page, a reply no shorter that keeps every held entry in its order (its new entries join), and a reorder only for the sort the viewer chose for that pane (`queueReorderSerial`), which must still hold every entry. It does not re-order the walk otherwise -- by last played the video just started comes first, and the step after it would go back to the one before -- and a reply missing a held entry is not taken. `EmbyPage::scroll` notes where a page was left when another was opened from it, and Back returns there once the page has arrived (`embyPendingScroll_`). Another folder, or a page newly opened, starts from its top.

The list follows a step. With the browser or the folder list open, `openAdjacentFile` (Page Up/Down, the bar's Previous and Next, the media keys, the menu's Previous and Next file) and `advanceAtEnd` (the playback order at a video's end) call `followStepInList` for the pane stepped, which notes `listFollow_`: the pane, the path it plays, and a deadline `kListFollowWaitMs` (5 s) on. A step at the end is followed only while a row showing the video that ended is in view (`panelRowInView`: its middle inside the content) and no press or drag holds the sheet, so a list scrolled away to look at something else stays there. `applyListFollow`, which `refreshPanelGeometry` runs once the sheet is laid out, waits for the pane's path to change -- a folder being read, the server's reply for the next episode -- and then for the list to show the new video (`listRowsShowing`: its row or tile, every place an Emby item is listed, or else the rows of the folders it is in, as the scrollbar marks them), and sets the scroll that brings the row of those nearest where the list is to its middle (`panelFollowScroll`), at every step, in view or not; the next frame is laid out there. A press on the sheet, the wheel over it, closing it or the deadline drops the follow. A video set's step, which changes every pane, is not followed, nor is the list's own Play or Add; the follow never changes the folder or page the list shows, though `localFollowVideo` still moves it to the only video's folder, and the follow then finds the row there.

The F6 sheet has two sources, `BrowserSource::Emby` and `BrowserSource::Local`. F6 follows the explicitly selected `Vn` target to its local folder (by `localFollowVideo`'s rule above) or Emby browser; `Ctrl+E` always opens Emby. A click on a video pane selects the target, while hover does not. `buildLocalRows` shares the browser's List and Thumbnails layouts but not Posters: a folder has no posters, and the shell's 16:9 thumbnail would only be letterboxed in a 2:3 tile. Its view is the toolbar's first button, `Thumbnails`, which switches between the list and thumbnails at a click over the same `EmbyBrowserPrefs::view` and is lit while they show; the browser's Posters shows as thumbnails there, lit, and stays the browser's choice until the list is chosen (`localToolbarAction`, `localSetView`). It marks every pane playing the same file, and provides a separate Add hit target on every row and tile. Local tile pictures use `file|<width>|<path>` keys. `LocalThumbnailer` (`LocalThumbnails.cpp`) asks `IShellItemImageFactory` on a worker thread in the multithreaded apartment, for a thumbnail or nothing, scaled by the shell to the size asked for, packs the bitmap as BMP bytes and delivers them from `pump()` on the window thread into the same `ThumbnailCache` the Overlay decodes with WIC; `clearPending` answers what was not started with `cancelled`. Its queue and flags are a state the worker shares, so closing waits only a second for a picture being made (a provider stuck on a share that went away), calling `CancelSynchronousIo` on the worker meanwhile, and then detaches it; joining it kept the closed player's process and its single-instance mutex alive for the SMB timeout, and a launch then was refused. The worker never runs a handler after closing. `embyRequestVisibleImages` keeps these keys in a queue of their own (`localThumbnailsInFlight_`, at most `kLocalThumbnailQueue` = 2: one job running, one waiting), apart from the server's 24, so the one shell worker never holds back an Emby poster and each place that frees goes to a tile showing then rather than to one scrolled past or of a folder left.

### Browser-managed local queues

## Seeking one video: keyframe landing, and the GPU wait outside the lock

A drag on the bar or an arrow key with one video loaded is a keyframe seek (`VideoSource::requestKeyframeSeek`, `keyframeSeek_` on): the worker seeks with FFmpeg to the keyframe at or before the target -- at or after it for a forward step, `direction` > 0 -- and, instead of gating frames until the exact target and prerolling through the GOP, takes the first decoded frame as the frame: it is published as the exact seek frame, the audio is re-aimed at its time under a new generation, and `takeSeekLanding` hands the owner where it landed; `App::tick` moves the clock to that time (`timelineForSourceTime`) and flushes the audio sink for the new generation. Several videos still seek exactly, or they would not stay in step.

GPU work can delay decoding when the renderer holds the shared device lock across `Present`. The renderer ends a frame by signalling an `ID3D11Fence` and arming an event, flushes, releases the lock while waiting, then re-locks for `Present`. Without fence support it uses an event query and a high-resolution waitable timer, taking the lock only while polling. `RenderStats` records the wait as `gpuWaitMs`; the `Perf` line reports it as `gpuwait=` separately from lock time. The Super Resolution extension is enabled only when a stream is magnified (`input.superResolution`), avoiding unnecessary enhancement work at or below its source size.

## Threads and pause correctness

Both conversion paths select BT.601/709 and full/limited range from each decoded
AVFrame. Software uses swscale colour details before each conversion; hardware
reads the retained owner frame and updates video-processor input/output colour
space before each blit, with automatic driver enhancements disabled. BGRA output
is full range. Unknown or unsupported matrices use BT.709 when original width
exceeds 720 or height exceeds 576, otherwise BT.601. Untagged YUV defaults to
limited range; RGB and legacy JPEG YUV default to full. Both rules
(`videoColorMatrixFor`, `videoColorFullRange`) also decide the matrix a
subtitle script's colours are corrected to. BT.2020 also takes this
approximation: there is no gamut conversion, transfer conversion or HDR tone
mapping.

Audio seek trimming uses integer 48 kHz output-sample positions. The decoder
seeks back by at least 50 ms (or the codec's larger seek preroll), then the gate
discards only samples preceding the requested position -- or, for a
generation started while the owner's clock runs, the position that clock has
reached (see the Time model). Frame timestamps are
adjusted for swresample delay, and EOF drains delayed output before Ended.
Initial missing PTS falls back to the requested origin and cannot establish
sample-exact source positioning.

The first known timestamp places a generation; after it the worker follows
the stamps rather than placing each buffer at its own (`AudioStampFollower`).
Placing each buffer at its stamp cut or skipped samples at every
disagreement past a tick, each a click: Matroska's millisecond stamps a block
early or late, an MP4 stamped a few samples off in turn, and one release
whose 48 kHz blocks are stamped at 44.1 kHz's pace, 8.85% ahead, where every
fifth block jumped the voice's clock by about 9 ms with no sound behind it,
until the re-aim about every 10 s. Now a frame's stamp less the running
sample count, smoothed over 0.1 s, sets how many samples
`swr_set_compensation` adds or drops across that frame, at most 10%: a
proportional term closes a difference over about half a second, and an
integral learns a stream whose stamps run at another rate than its samples.
However long the frame, one observation closes at most half the difference
and learns at most a quarter of it, so codecs whose frames are near a second
long settle instead of overshooting further each frame, and nothing is learnt
while the stretch is pinned at its limit. The rate is kept across seeks of
the stream and forgotten on a track change. A frame's compensation is spread
over the frame's own length but always over more samples than it adds
(`AudioStampFollower::compensationDistance`): a frame under half an output
sample long -- 1 sample at 176.4 or 192 kHz, 1-3 at 352.8 or 384 kHz --
rounds to none, and at a distance equal to the samples added
libswresample's input step is zero and it divides by it. Until 2026-10-26
the worker gave a frame its rounded length plus the samples added, at least
1, which is that distance for such a frame, and the integer divide by zero
on the audio thread ended QuadDeck.

What is not a small disagreement is not bent into the sound. Each stamp is
measured against the line the ones before it set -- where the last one in
line, the rate and what was added put it, or, after a placement, where the
placement did -- so neither a step still being eased nor the loop's own lag
counts. One more than 15 ms off it (or 15% of a frame over 0.1 s, more
than a rate not yet learnt moves a frame's stamp) is held over, a frame or
two, until the stamps show which line they keep. Back on the old one, the
stamps held over were out of line and are passed over, however far out; off
every line three frames running, the stamps are only uneven, and the third
is passed over as well, the line kept and the next stamp judged afresh,
unless the loop has lost them (below). On
a new line, the step is the stamps' own: the loop
is shown the stamps less the step, and the count eases onto it at 0.5% on
top of the loop's stretch, within the 10%, cutting and adding nothing, so
the buffers' times run on without a jump. A 100 ms step takes 20 s, and a
second step adds to what is left of the first; 0.5% is about 9 cents, and
meanwhile the pane's sound is off its stamps by what is left. A step that
would leave the count more than 100 ms off the stamps, what is still being
eased counted in, is not eased: ahead, it is a gap, put in as silence up to
10 s; back, or past 10 s, the sound is placed again, the high-water mark
cutting what was already sent. Either is taken a frame or two late, after
the frames that showed it. So is the loop losing the stamps by 100 ms, as
it does on stamps more than 10% ahead of their samples -- a stamp held over
only for that, though on the line, is no line of its own, and the next one
agreeing with it finds the loop lost rather than a step to ease; on frames
over half a second, by a fifth of a frame, since the loop moves the count
at most 10% of a frame each frame and, learning a rate near that, trails
the stamps by more than 100 ms. Stamps running further from their samples
than the 10% may follow move, on frames of 0.1 s or more, more than 15% of
a frame each frame, so each is on no line; with the count more than 100 ms
(or a fifth of a frame) off them and all three held over off the line the
same way, they are lost as soon as three running each run further away, or
after six on no line, and the count is never further off than that and six
frames of the drift (three when they run away evenly). Stamps that stand
still or go back, each less than a fifth of a frame past the last (the
line itself moving on by the learnt rate), are no clock: they are passed over however far, and the sound goes on by the
count. On such long frames a step under 15% of a frame is within
the line, and the loop follows it, bent into the sound at up to 10%. Stamps
that wander more than about 7 ms from one to the next, which real streams
rarely do, are now and then taken for steps; so, on frames of about 0.1 s, are
every other stamp 7 ms or more out on a stream whose rate near 8-10% is not
yet learnt, and then it is never learnt and the stream is filled every
second or so; and, with a few ms of jitter, stamps just past the 10%,
the count up to about 200 ms off before each Fill. Stamps on a grid of
150-200 ms that run 1% or more off their samples are never learnt
either, the count up to about 0.6 s off between placements. After a seek, a frame that the count
and its own stamp both put wholly before the target -- or, after a
placement back, one the count puts over sound already sent -- is placed on
its own stamp, since none of it is heard. The first frame that would be
heard, if its stamp and the count put it more than 15 ms apart, is
converted and kept back until the next stamp shows which of the two it
follows on from: its stamp, as after a gap at the target, and it is placed
there, after silence; the count, and its stamp was out of line. With no
stamp after it, it goes at the count. A 48 kHz stream goes through
swresample untouched until its first compensated frame starts the filter, so
exact stamps stay sample-exact; the filter starts against a reflection of
the samples it is given, which bends a few samples by about 3% of one
sample's change, near 24 kHz. Fills, steps eased onto (with how much is
then being eased) and placements (eight a stream) and, once, a rate past 1%
held for five seconds are logged as `Audio timestamps ...`. Sound lost to a
refused packet is credited by the worker, not left to the follower: the
packet's duration at 48 kHz, or the last frame's length for a receive error
or a packet with no duration, and the time up to the next packet's stamp,
since FFmpeg's MPEG-audio parser joins garbled bytes to the next frame under
one frame's duration. At the next decoded frame a step ahead within that
credit and the tolerance (and `kFillLimit`) is filled with silence, with no
`Audio timestamps` line, and the follower starts again; the credit clears
there, at a seek and at each move of a look at the start. Without it the
follower would take the loss for a step in the stamps and play the sound
after it early by all of it, 21-24 ms a frame, until eased back at 0.5%;
until 2026-10-26 a refused packet silenced the sound until the next seek.

In Matroska the audio worker seeks by the video stream instead
(`audioSeekPoint`). The index (Cues) of nearly every Matroska file, as
mkvmerge and FFmpeg write it, lists only the video's keyframes, and FFmpeg
seeks a stream the index leaves out by reading the file from its start to the
target: on a network share, tens of seconds deep into a long film, silence
the whole time and the video's reads queued behind it. By the video's entries the demuxer lands in the cluster of
a keyframe before the target in milliseconds. It drops the audio block that
began before that keyframe, so this seek aims at least 1 s early
(`kAudioSeekByVideoLeadSeconds`), past any audio block's length, and the gate
above discards the rest. A target within that lead of the video's first frame
seeks by the audio stream, which reads only the start of the file.

Each source owns separate video and audio demux/decode threads. Both FFmpeg format contexts are allocated explicitly and carry an interrupt callback tied to the source's running flag, which ends an HTTP open, stream probe or read that polls it before the workers are joined. It cannot end everything: FFmpeg's file protocol, which local and share files use when the NAS cache is off or bypassed (a file another program holds open for writing), reads with a plain synchronous read that never asks it; the read-ahead cache's worker waits for a cancelled read to complete; a host name lookup is not interruptible. So the window thread does not close sources itself. `App::retireSource` hands a source, already silenced and its voice flushed, to `SourceReaper`: `VideoSource::beginClose` tells its workers and its cache to stop at once, and `close()` then joins them on a thread of its own, so a read stuck on a share that stopped answering no longer freezes the window and the other panes until the redirector gives up, and several panes closing do not wait for each other. Its late audio carries the flushed generation and is refused by the voice. At most `SourceReaper::kMaxClosing` (4) close at once; a fifth waits, so stuck sources and their decoder memory cannot pile up. Device recovery drains the reaper before the device is let go (the closing decoders hold it), and `WM_DESTROY` drains it before the audio output and renderer go; both still wait there as before, and the reaper is App's last member, so it is destroyed, and drained, first. FFmpeg D3D11VA, rendering and DXGI presentation share one D3D11 device/immediate context and one recursive mutex. The renderer keeps `Present(1, 0)` inside that critical section so presentation cannot race a hardware decoder's immediate-context work. The App waits on the frame-latency object outside the mutex when available; fallback presentation can wait for vertical blank while holding it. Each pane's XAudio2 SourceVoice frequency ratio is that pane's playback rate over the tempo its queued sound was already stretched to (1 unless pitch is kept); the common mastering voice owns master volume and mute. When XAudio2 stops on a critical error (the endpoint it plays to went away with no other to move to), its callback only records the HRESULT; `App::serviceAudioOutput`, from the tick, logs `Audio engine stopped:` and reopens the output 300 ms later, as it does when the outputs change (see Audio output and effects). A failed start logs `Audio output unavailable:` with the failing call, and a failed reopen is logged once until one succeeds. Device reconstruction keeps the renderer's lost-device latch raised until device, pipeline and back buffer all succeed. A failure that raises the latch is a lost-device code, or any failure after which `GetDeviceRemovedReason` reports the device gone; anything else (out of memory, an invalid call) never starts a rebuild, which would tear every decoder down. A resize the swap chain refuses keeps the old size: `resizeBackBuffer` gives the chain that size back (it may have kept its buffers or let them go) and makes the render target on it, so the picture goes on stretched to the window, and the size the window asked for waits. `render` no longer stops at a missing render target: under the device lock it tries again about once a second (`retryBackBuffer`) for a waiting size or for a target that resize, the output-mode switch or its fallback could not make, logging the first failure, every 60th after it and the recovery. Until 2026-10-13 such a failure left the target null and every frame returned early with no retry, so the picture froze until the window was resized again. App tears decoder sources down only on the first attempt and retains that attempt's master position and resume intent across transient failures, so a later successful retry does not return as a permanent black paused deck. Paths remain logical occupied slots during the retry interval: open/drop/close/session operations update that logical state, while D3D11VA source construction and shader creation are deferred until a valid device exists. An Emby stream address that arrives in that interval is kept with the time it starts at but opens no decoder; the rebuild asks the server again. A failed rebuild is tried again after 1, 2, 4 ... seconds and then every 30 for as long as the device stays lost (`deviceRecoveryDelay`), and `WM_DISPLAYCHANGE` brings the next try forward. Before each try the overlay lets go of its Direct2D device (`Overlay::releaseDeviceResources`; the DirectWrite and WIC factories stay, so text is still measured) and the tick drops the frames it drew, and `D3DRenderer::releaseDeviceResources` flushes the context after the swap chain goes: a flip swap chain is destroyed at that flush, not when it is let go, and while anything else holds the device the window refuses a new chain with E_ACCESSDENIED. Until 2026-10-12 nothing flushed, and recovery stopped for good after five failed tries. Play, pause, stop and seek update the saved recovery intent rather than appearing to work and then being overwritten. Renderer shader creation also checks the device under the shared recursive mutex, so an unexpected caller cannot dereference a released device.

Every flag a `VideoSource` or `ReadAheadCache` wait tests changes under that object's mutex, the stop flags (`running_`, `stopped_`) and `audioEnabled_` included, and the notify follows once the mutex is released. They are atomics and are read without the mutex elsewhere, but a worker tests its wait's condition under the mutex and sleeps only afterwards, so a store made without it could land, and notify, between the two, and the worker would sleep through it. For `close()` that was permanent: the video worker parked on a full queue and the audio worker waiting to be enabled have no timeout, and `close()` joins both on the window thread, which then froze. This explains one possible replacement hang; it has not been confirmed as the cause of a real-player incident. The window thread calls `frameForTime` and `setAudioEnabled` for every pane every tick, so they notify only when something a wait tests changed: a frame taken off the queue, the audio switched. Until 2026-10-13 both notified on every call and woke both workers of every pane for nothing.

Seeking uses FFmpeg's backward keyframe seek. The decoder must process dependency frames between that keyframe and the requested timestamp, but the video target gate prevents them from entering the render queue. User-visible seconds are converted to the nearest integer stream tick with finite/range checks and saturating origin addition; truncation is deliberately avoided because binary rounding can otherwise turn an exact boundary such as 2.001 seconds in a millisecond time base into the preceding tick. Video and audio use the same conversion. The gate compares integer `best_effort_timestamp` values in stream time-base units and treats a frame as preroll only when its half-open PTS interval ends at or before the target. `AVFrame::duration` defines that interval; when it is absent, `av_guess_frame_rate` supplies a nominal duration rounded upward to whole stream ticks, and a stream with neither falls back to the first PTS at or after the target. This avoids the old fixed 50ms gate selecting multiple expired frames at high frame rates. The worker retains only the most recent raw preroll frame so an EOF seek can promote the final frame once when the requested endpoint lies outside every half-open interval; this defers software conversion and pins at most one extra D3D11VA surface. If the seek's gate is still open at the end of the stream with no such frame, `endSeekWithHeldFrame` pushes the picture on screen (`heldFrame_`'s own `AVFrame`) as that generation's exact frame; with no picture up it stores the generation in `seekEndedWithoutFrame_`, unless the seek has been replaced. Either way it logs one line: `The seek to X s reached the end of the stream with no frame of its own; the picture up, at Y s, stands as its frame`, or `...; no picture is up to stand in, and the seek barrier waits for none from it`. The audio worker uses its own target-gated strategy after flushing its decoder and resampler. A newer pending seek supersedes frames from an older request.

Timeline moves take one of two styles. A synchronized seek freezes the clock until every participating pane has decoded its own exact destination frame, so playback resumes with all participating panes aligned; its cost is bounded by the keyframe interval. A fast seek keeps the clock running and lets each pane show its nearest keyframe and converge on its own. Seek-bar drags and relative keyboard seeks are fast, because both are coarse positioning where waiting for the slowest decoder dominates the interaction. Starting playback, master A-B loop wraps, repeat-all restarts and every re-alignment after a structural change (offset edits, pane swaps, decoder changes) stay synchronized.

Fast timeline and relative keyboard seeks enable a two-stage presentation path. The first decoded keyframe may be published once as a static preview only when it is no more than 15 seconds before the exact target; if that keyframe is older, the seek has no preview. Every subsequent dependency frame remains suppressed until the target frame's presentation interval reaches the requested PTS. Software decode sets `skip_frame`/`skip_idct` to `AVDISCARD_NONREF` and skips loop filtering during invisible preroll, restoring full quality 750 ms before the video-stream-clamped decode target. Using the video stream's own final tick here prevents longer audio or container padding from keeping non-reference-frame discard active through EOF. Both demux contexts mark unrelated streams `AVDISCARD_ALL`. Synchronized structural seeks do not request a preview.

Whatever the style, the pane keeps its picture through the seek. `requestSeek` empties `currentFrame_`, so `frameForTime` hands out nothing until the seek's own first frame -- the preview, the keyframe landing or the exact frame -- but `VideoSource::heldFrame` still returns the last frame `frameForTime` handed out, and `App::tick` draws that in place of a null frame (the renderer's slot still holds its texture, so nothing is converted again). The held frame is the same object as `currentFrame_` whenever that is set, so the pair pins at most one decoder surface, and `close` releases it. The barrier and the first-frame log are shown only frames `frameForTime` returned for this time, so a held picture can neither release a synchronized seek nor be recorded as its first frame, unless `endSeekWithHeldFrame` queues it again as the exact frame of a seek that reached the end of the stream with none of its own; and the paused drain after a seek backwards still starts from nothing rather than taking the held picture's later time for a malformed stream.
`SyncState.hpp` holds the rules themselves, free of Win32, D3D11 and FFmpeg: `PaneTiming` describes one pane, `mappedPaneTime`/`paneBeforeEnd`/`shouldOutputPaneAudio` derive its local time and audio eligibility, `audioHandoff` picks the successor when a selected source's video or audio finishes, and `SeekBarrier` owns the per-pane wait, video/audio generation and frame-ready state that `App` previously kept in parallel member arrays. Audio has four generation-scoped states: Unknown still waits, while Primed, Ended and Error are terminal for the audio half of the barrier. Ended/Error never waive the exact-video requirement. Besides a pane that has failed (`PaneStatus::errored`), which the barrier skips altogether, the one exception for video is a pane whose seek of the barrier's generation ended with no frame to show: `App::paneStatuses` passes `seekEndedWithoutFrame` in `SeekBarrier::PaneStatus`, and `SeekBarrier::ready` then waits for no frame from that pane for that generation, though it still waits for its sound. Until 2026-10-26 a decode error in a damaged last stretch ended its pane instead, which the barrier skips as failed, while a last stretch that decoded to nothing without one held every pane for `kTimeoutMs`. A short, missing or broken audio stream no longer parks otherwise-ready video until the 30-second fail-safe. `App` supplies the decoder- and device-dependent facts through `PaneTiming` and `SeekBarrier::PaneStatus`, and the barrier reports elapsed time rather than reading a clock.

Every video seek has a monotonically increasing generation. Frames carry that generation plus an exact-target marker, so a frame decoded for a superseded request cannot satisfy a newer synchronization operation. Audio seek state carries its own process-wide generation, and the barrier accepts audio readiness only when that generation matches the request it recorded. A global seek issued while playing pauses the master clock, all SourceVoices and all source audio producers. `App` continues calling `frameForTime(..., advance=false)` to show an allowed static keyframe preview, but does not resume until every active, non-paused, non-finished source has returned an exact frame for its recorded generation and that frame is included in the same render call. The barrier then seeks the frozen clock to the requested master time and starts all selected audio voices and the clock together. Pressing Pause while the barrier is active disables and flushes its audio prefetch immediately; pressing Play again creates replacement audio generations at the unchanged target. A 30-second fail-safe prevents a broken video source from deadlocking playback. First-frame, exact-frame, generation-scoped audio state and barrier timings are appended to `QuadDeck.log`. `Diagnostics.hpp` is the single writer: one process-wide mutex serializes the decoder, renderer and application records, every line includes a local timestamp to milliseconds and the Windows thread ID, the path is resolved once from the executable's own directory (falling back to `%LOCALAPPDATA%\QuadDeck` when that is not writable) rather than from the working directory, and once the file passes 4 MiB it is moved to `QuadDeck.1.log`, replacing the one before, and a new file begins (only if that move fails is the file emptied instead). A report written just before the limit therefore survives at least another 4 MiB of records. Packaging starts from a fresh allow-list staging directory, copies only the app-local Release DLLs and never puts diagnostic logs or the PDB in the archive; the unpacked `dist\QuadDeck` gets `QuadDeck.pdb` and keeps the replaced build's `QuadDeck.log` and `QuadDeck.1.log`.

A frozen window thread is what Windows reports as "stopped interacting with Windows"; it keeps no dump of it. `HangWatchdog` (in `App::run`) is a thread of its own that `renderFrame` beats once per frame. `renderFrame` also runs from the modal-loop timer, so menus, dialogs and window drags keep beating, and only a window thread that is waiting on something goes silent. `StallTracker`, pure, decides when to look: after 4 s of silence and again after 10 s (stuck or slow), never a third time in one stall, a recovery line when beats return, and nothing when the watchdog's own polls were seconds apart (the machine slept). To look, `reportAllThreadStacks` first lists the loaded images and their unwind tables (through the process's module list and `ReadProcessMemory`, never the loader lock), then suspends every other thread in turn and unwinds its stack into a preallocated array, touching no heap or lock while a thread is suspended, since that thread may hold either. That is why it searches each image's `.pdata` itself instead of calling `RtlLookupFunctionEntry`, which takes ntdll's function-table locks that a thread loading or unloading a DLL holds exclusively, and why it reads only the committed stack region the thread's stack pointer is in and stops at code outside every image. Once all threads run again the stacks are written as module offsets, before dbghelp is started; dbghelp, given the listed modules rather than walking the loader's list itself, then names the frames in a second record (`HANG names, look N of 2:`), QuadDeck's own from `QuadDeck.pdb` beside the executable (the Release build is linked with `/DEBUG /OPT:REF /OPT:ICF`), other DLLs by their exports. A dbghelp that is slow, or waits on a lock the stalled thread holds, costs the names but not the stacks. The window thread comes first, and threads with identical stacks are folded. The report goes through `appendDiagnostic`, so a window thread stuck inside the log's own mutex would stop it too. So that a report can be read against the right source, `App::run` begins the log of every run, before the watchdog starts, with `describeBuild` (`Diagnostics.hpp`): the version, the commit (`-dirty` when tracked files differed from it) and the configuration, which CMake generates into `BuildInfo.cpp` at configure time (`BuildInfo.hpp`), then the executable's link time stamp and the GUID and age of the PDB it matches, read from its own headers. Servers see only the version: the Emby client version and the user agents (`buildUserAgent`) carry `PROJECT_VERSION` and never the commit. CMake refuses to configure when `vcpkg.json`'s version differs from `PROJECT_VERSION`.

Video enqueue rechecks its pending-seek state after expensive software conversion. Audio resampling rechecks its generation, and the destination voice independently rejects chunks at or below its flush watermark while holding the same per-voice lock used by submission. The App-side order is therefore disable producer, allocate the replacement seek generation, flush/rebase the voice while preserving that generation, then re-enable it. Both the right-click menu and the settings window route per-pane repeat changes through that same App operation. Repeat and per-pane A-B edits sample the running master clock once for both old and new mappings; if the current mapping is unchanged, they change future policy without flushing either decoder, while a genuine remap follows the generation-safe reset order or rebuilds an active global barrier. Resuming a pane recomputes its mapped target after clearing the paused flag, because loop/repeat policy deliberately does not affect the paused pane's frame and may have changed while paused. Together these checks close the race where work from a superseded request could otherwise refill a queue after `requestSeek` and the XAudio2 flush, briefly exposing an old frame or audio chunk.

When globally or individually paused, `frameForTime(..., advance=false)` can prime a frame after open/seek but does not drain the decoded-frame queue. This prevents malformed or sparse timestamps from letting the picture continue for several seconds after pause.
